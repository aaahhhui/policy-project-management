# 项目记忆：政府科创政策收集与项目申报管理系统

> 更新日期：2026-07-29
> 用途：保存后续产品设计、实施计划和开发过程中必须持续遵循的已确认决策。  
> 完整设计文档：[`docs/superpowers/specs/2026-07-23-policy-project-management-design.md`](../docs/superpowers/specs/2026-07-23-policy-project-management-design.md)

## 1. 产品定位

- 这是面向公司内部团队的 Web 系统，不是微信小程序，也不是对外销售的通用 SaaS。
- 公司约 200 人，处于铸造仿真行业；科技项目或政府项目申报只是公司业务方向之一。
- 首期预计 5—15 名用户。
- 核心闭环：政策发现 → 原文留痕 → 多经营主体评估 → 负责人确认 → 团队通知 → 政策转项目 → 项目结果追踪。
- 首期目标是 2—3 周内完成可上线验证的 Demo，而不是一次建设完整的大型申报管理平台。

## 2. 用户与权限

系统不设置“系统管理员”业务角色。

### 申报负责人

- 首期由同一个人承担政策确认、业务配置和项目统筹。
- 可以维护账号与角色、企业档案、经营主体、政策来源和评估规则。
- 可以确认或修改政策结论、指定主要申报主体、政策转项目及管理全部项目。

### 项目对接人

- 可以查看全部政策和项目。
- 只能更新自己负责项目的状态、提交日期、结果日期、进展说明和结果说明。
- 不能修改政策结论、评估规则、企业档案、主要申报主体、关联政策或其他项目。

### 项目成员与产品规划团队

- 可以查看全部政策、评估明细和项目。
- 首期不具有业务修改权限。

### 通用规则

- 所有内部用户均可查看全部政策和项目，首期不做部门或经营主体级数据隔离。
- 关键修改必须记录操作人、时间和修改前后内容。
- 首期采用账号密码登录，保留企业微信登录扩展能力。

## 3. MVP 范围

### P0

- 企业共享档案与多个经营主体档案。
- 5 个重点来源的每日自动采集。
- 政府网站、协会网站、公众号文章链接及自定义网址。
- 单条政策链接录入。
- 政策解析、去重、原文及附件留痕。
- 结构化规则、加权评分、DeepSeek 分析和人工确认。
- 企业微信群机器人通知。
- 政策转项目与轻量项目台账。
- 权限、操作日志、任务日志、通知日志和每日备份。

### 不进入 P0

- 微信小程序。
- 申报材料协作、任务拆分和文件版本管理。
- 一条政策生成多个项目。
- 任意网站 100% 自动识别。
- 验证码破解、登录绕过或不合规采集。
- Redis、Kafka、Kubernetes、微服务和多节点容灾。

## 4. 政策业务规则

### 用户可见结论

- 待确认
- 建议申报
- 持续关注
- 暂不建议申报
- 无法判断
- 已转项目或已归档（后续业务标识）

### 结论展示

- 每条政策始终只显示一个当前结论，不能同时显示“系统结论”和“负责人结论”。
- AI 已给出建议但负责人尚未确认时，使用弱化或虚线状态表现。
- 负责人确认后，使用正式、实线状态表现。
- “待解析”“待评估”等仅是后台处理状态，不向用户展示。
- AI 重新评估不得自动覆盖负责人已经确认的结论。

### 多经营主体

- 同一条政策可以分别评估北京、苏州、深圳等经营主体。
- 各主体结果作为评估明细，政策层面仍只有一个当前结论。
- 当负责人确认“建议申报”时，必须同时指定一个主要申报主体。
- MVP 中一条政策最多生成一个项目，项目绑定该主要申报主体。

### 政策字段

- 政策名称后紧跟当前状态。
- 必须展示发布日期和申报截止日期。
- 必须保留来源网址、采集时间、原始网页和附件入口。

## 5. 项目业务规则

项目状态为：

`待申报 → 已提交 → 成功 / 未通过 / 终止`

- “申报准备”和“审核中”已明确删除。
- 项目只做轻量台账，不做任务、材料和版本协作。
- 一条政策在 MVP 中最多对应一个项目。
- 项目对接人只能修改自己负责的项目。

## 6. 企业档案

- 公司级共享档案保存业务方向、技术能力、产品、人员和通用研发情况。
- 北京、苏州、深圳作为不同经营主体管理。
- 北京、苏州暂按独立法人初始化。深圳公开名称为“深圳适创腾扬科技有限公司”，与原“非独立分公司”假设冲突，主体类型须以营业执照或国家企业信用信息公示结果终审，开发不得写死。
- 主体级资料包括注册信息、法人属性、资质、知识产权和研发数据。
- “编辑档案”和“更新公开信息”属于经营主体级操作，按钮放在对应主体区域。
- 研发投入比例不设置独立编辑入口，统一在经营主体档案中编辑。
- 只使用公开企业信息和公司内部非保密资料。

## 7. 政策来源与采集

- 首期每天采集一次，优先保证 5 个重点来源。
- 负责人可以配置、启停来源，并添加自定义网址。
- 添加来源使用右侧抽屉或全局弹窗，不把表单直接展开在来源列表页。
- 重点来源需要独立适配器；通用解析只作为自定义网址的补充，不承诺适配所有网站。
- Scrapy 是主要采集方式，只有必须运行页面脚本的网站才使用 Playwright。
- 去重综合使用标准化网址、标题、发布日期、文号和内容哈希。
- 已收录政策内容发生变化时保留版本并重新评估，不直接覆盖历史内容。

来源健康状态：正常、偶发失败、连续异常、已停用。

- 单次采集失败只在系统中记录。
- 连续 3 次失败后，通过企业微信群机器人通知负责人。

## 8. 评估机制

评估由三层组成：

1. 硬规则：地区、主体类型、成立年限、资质等明确条件。
2. 加权评分：政策方向、技术匹配、企业能力、申报价值和准备难度等。
3. DeepSeek 语义分析：提取政策条件、解释匹配度、形成依据和风险点。

- 评估规则可以由负责人编辑。
- 规则修改形成新版本，历史评估保留当时使用的规则版本。
- 系统只展示清晰结论，并提供评估明细入口。
- DeepSeek 是辅助分析工具，负责人是最终决策人。
- DeepSeek 模型名称、地址和参数必须配置化，不能写死在代码中。

## 9. 通知

首期只使用企业微信群机器人，不建设企业微信自建应用。

通知场景：

- 高匹配政策发现。
- 政策评估完成。
- 政策转为项目。
- 项目已提交。
- 项目申报成功。
- 政策来源连续 3 次失败。
- 每日备份失败。

通知失败需要重试并保留失败记录。群消息只放摘要和详情入口，不在群内完成复杂业务操作。

## 10. 关键页面决策

- 政策中心采用已确认的 B 方案列表布局，并增加分页。
- 政策详情、评估明细和负责人确认放在同一页面，按阅读和决策顺序连续呈现。
- 确认按钮与负责人修改状态控件集中在同一操作区域。
- 项目台账不展示状态图例和说明提示块，增加分页。
- “3 条政策可转项目”使用文字按钮，放在申报项目总结下方。
- 移动端采用响应式 Web，只支持查看政策、查看评估明细和确认结论；不承担政策转项目和项目维护。

## 11. 技术架构

架构采用“模块化单体业务应用 + 独立爬虫运行区”。

| 层级 | 选型 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite、Element Plus |
| 业务 API | Python、FastAPI |
| 数据访问 | SQLAlchemy 2、Alembic |
| 数据库 | MySQL 8.4 |
| 爬虫 | Scrapy、scrapy-playwright、Scrapyd |
| 正文提取 | 来源专用规则优先，Trafilatura 兜底 |
| 定时任务 | APScheduler |
| AI | DeepSeek API 适配层 |
| 部署 | Ubuntu Linux、Docker Compose、Nginx |

关键原则：

- 业务后台保持一个代码库，但按账号、政策、企业档案、评估、项目、通知和审计划分模块。
- 爬虫独立运行，爬虫异常不能影响政策查看和项目管理。
- AI 评估和通知使用后台任务，页面不等待外部接口返回。
- MySQL 保存结构化数据和运行记录；原始网页和附件保存在独立文件卷。

## 12. Demo 部署与正式迁移

### Demo 已确认方案

- 个人实名认证的腾讯云账号。
- 中国香港 Lighthouse 轻量应用服务器。
- Ubuntu LTS 64 位。
- 推荐 4 核 8GB、80GB 以上系统盘。
- 先按月购买。
- Docker Compose 部署。
- 只保存公开、虚构和内部非保密数据。

使用香港地域是为了不等待中国内地 ICP 备案，允许少量跨境网络波动。它只用于验证，不是公司正式生产环境。

### 正式环境

- 迁移到公司企业账号下的中国内地标准 CVM/ECS。
- 使用公司域名、HTTPS 和单位主体备案。
- 迁移 MySQL、原始文件和附件，并更换全部正式密钥。
- 不依赖个人账号直接转让资源，采用标准备份和重新部署完成迁移。

## 13. 安全与备份

- 密码使用安全哈希保存，并限制连续错误登录。
- MySQL 不直接暴露互联网，公网只开放必要的 HTTPS 入口。
- SSH 只允许必要的管理来源访问。
- DeepSeek 密钥、群机器人地址和数据库密码不能写入代码或版本库。
- 数据库、原始网页和附件每天异地备份一次，保留 7 天。
- 上线前必须实际完成一次数据库和文件恢复演练。
- 当前备份方案最多可能损失一天内的新数据和操作记录。

## 14. MVP 验收指标

- 5 个重点来源采集覆盖率不低于 90%。
- 政策发布后 24 小时内进入系统。
- 政策来源可追溯率达到 100%。
- 政策负责人每周人工投入从 2—5 小时降至 1—2 小时。
- 一条政策可完成采集、原文留痕、多主体评估、负责人确认、通知和转项目完整闭环。
- 项目对接人无法修改其他人负责的项目。
- 连续 3 次采集失败能够触发异常通知。
- 备份能够成功恢复。

## 17. 2026-07-29 下一阶段确认结论

- 下一阶段优先闭合“政策评估决策”链路，不在本阶段继续扩展项目管理链路。
- 已确认的业务流程为：`评估规则发布 → 真实 DeepSeek 多企业评估 → 负责人复核与确认 → 确定唯一主申报企业`。
- 本阶段必须完成：
  - 评估规则的草稿、发布、停用和不可变版本历史；已发布规则调整时创建新版本。
  - 硬性条件、加权评分条件和权重校验；新评估固定引用一个规则版本及其快照。
  - 接入真实 DeepSeek API，对北京、苏州、深圳三家经营主体分别生成结构化评估结果。
  - 保存模型、提示词、规则版本、企业档案快照、请求标识、Token 用量和重试信息；API Key 不得进入数据库、前端或日志。
  - DeepSeek 调用采用异步批次、严格 JSON 校验和有限重试；三家企业结果全部验证通过后才允许原子入库。
  - AI 评估完成后进入待确认状态；负责人可接受或修改建议，修改时必须填写原因。
  - AI 原始结果与人工最终结果分别保存；已确认批次不可编辑，重新评估必须生成新批次并保留历史。
