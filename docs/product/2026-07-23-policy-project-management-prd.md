## 0. 结论摘要

MVP 建设一条真实可用的纵向闭环：系统每天从 5 个重点来源采集政策，保留原文和附件，结合公司共享档案及北京、苏州、深圳等经营主体进行结构化和 AI 评估，由申报负责人确认唯一结论，并通过企业微信群通知团队；确认建议申报的政策可以指定主要申报主体并转为唯一项目。

首期只解决政策发现、评估确认和轻量项目进度追踪，不建设微信小程序、申报材料协作、复杂任务管理或分布式基础设施。

## 1. 项目背景

### 1.1 公司与业务背景

- 公司约 200 人，处于铸造仿真行业。
- 科技项目或政府项目申报是公司业务方向之一，不是公司的唯一业务。
- 系统首期预计 5—15 名内部用户。
- 当前没有既有系统，不设置“系统管理员”业务角色。

### 1.2 当前问题

1. 国家部委、地方政府、协会和公众号等政策来源分散。
2. 负责人需要借助 AI 工具、咨询平台和人工浏览进行收集，每周投入约 2—5 小时。
3. 政策无法及时同步团队，原文、判断依据和历史结论缺乏统一沉淀。
4. 政策是否适合不同经营主体缺少统一评估标准。
5. 申报项目进度依赖人工沟通，状态变化和结果缺少可视化追踪。

## 2. 产品目标与成功指标

### 2.1 产品目标

- 自动发现并统一沉淀重点政策。
- 保证政策原文、来源和评估依据可追溯。
- 形成“规则 + AI + 人工确认”的统一判断流程。
- 支持一个公司下多个经营主体分别参与政策评估。
- 将建议申报的政策顺畅转为项目，并持续追踪结果。

### 2.2 MVP 成功指标

| 指标编号 | 指标 | 目标 | 验证方式 |
|---|---|---:|---|
| KPI-01 | 5 个重点来源采集覆盖率 | ≥ 90% | 连续两周按来源人工抽样核对 |
| KPI-02 | 政策发布至系统入库时间 | ≤ 24 小时 | 比较发布日期与首次入库时间 |
| KPI-03 | 政策来源可追溯率 | 100% | 检查政策来源、原网址和采集记录 |
| KPI-04 | 关键状态修改可追溯率 | 100% | 抽查政策确认和项目状态历史 |
| KPI-05 | 每周人工投入 | 由 2—5 小时降至 1—2 小时 | 负责人试用期记录 |

## 6. 全局业务规则

### 6.1 单一结论规则

- 政策列表和详情页只显示一个当前结论。
- 不并列显示“系统结论”和“负责人结论”。
- AI 结论未确认时通过弱化或虚线样式表达，不新增第二个状态字段给用户。
- 负责人确认后使用正式样式。
- AI 重新评估不得覆盖已确认结论。

### 6.2 多主体规则

- 每条政策分别评估所有启用的经营主体。
- 各主体结果进入评估明细。
- 政策层面汇总为一个当前结论。
- 确认“建议申报”时，必须指定一个主要申报主体。
- 其他结论可以不指定主体。

### 6.3 一对一转项目规则

- MVP 中一条政策最多生成一个项目。
- 只有负责人可以转项目。
- 政策必须已经确认且结论为“建议申报”。
- 主要申报主体必须已指定。
- 已转项目的政策不能再次生成项目。

### 6.4 中间状态隐藏

- 待抓取、待解析、待评估、AI 调用中和通知重试中均为后台任务状态。
- 用户业务页面不展示这些技术中间状态。
- 负责人可在任务记录中查看失败和重试情况。

### 6.5 列表字段统一规则

#### 6.5.1 字段类型

| 类型 | 说明 | 通用校验与展示规则 |
|---|---|---|
| 文本 | 名称、文号、说明等 | 去除首尾空格；必填文本不得只包含空格；超长内容在列表中省略，详情中完整展示 |
| 单值枚举 | 状态、类型、角色等 | 只能使用 PRD 定义的枚举值；停用值不得用于新数据，历史数据仍可展示 |
| 多值枚举 | 地区、政策类型、角色等 | 去重保存；列表中以标签展示，超出可视范围时折叠并显示数量 |
| 日期 | 发布日、截止日、提交日等 | 保存为日期值，统一展示 `YYYY-MM-DD`；未知时显示“—”，不得用虚构日期填充 |
| 日期时间 | 采集、更新、操作时间等 | 系统生成，统一展示 `YYYY-MM-DD HH:mm`；按用户所在时区显示，Demo 默认东八区 |
| 布尔值 | 启用、停用、是否转项目等 | 页面使用明确的状态文案，不直接显示 `true/false` |
| 数值 | 权重、评分、连续失败次数等 | 必须校验允许范围；列表中的小数位按字段规则统一 |
| URL | 来源地址、原文和附件地址 | 仅允许 `http` 或 `https`；保存原值和标准化值；列表省略显示但支持打开完整地址 |
| 关联对象 | 经营主体、政策、项目、用户等 | 保存对象唯一标识；列表显示对象名称；关联对象停用后历史名称仍保留 |
| 派生字段 | 健康状态、是否过期、当前结论样式等 | 用户不可直接编辑，由系统按照明确规则计算并可追溯计算依据 |

#### 6.5.2 字段来源

| 来源类型 | 说明 | 冲突处理 |
|---|---|---|
| 人工录入 | 负责人或有权限用户填写 | 已确认的人工值优先级最高，不被自动任务静默覆盖 |
| 网页解析 | 从政策原网页或附件提取 | 必须保留来源网址、采集时间和内容版本 |
| 公开信息更新 | 从企业公开信息来源获得 | 只更新公开字段，不覆盖内部补充字段 |
| 关联继承 | 从政策、经营主体或用户等关联对象继承 | 来源对象变化时按字段规则决定同步或只保留历史快照 |
| 系统生成 | ID、时间、状态历史、任务结果等 | 用户不可编辑，必须记录生成时间和关联对象 |
| 系统计算 | 健康状态、评分、连续失败次数等 | 保存或能够重建计算依据，不允许只保留最终显示值 |
| AI 生成 | 摘要、匹配依据、风险点等 | 必须关联模型配置、评估批次和输入版本；人工确认值优先 |

#### 6.5.3 通用校验与空值规则

- 必填字段保存失败时，在字段附近提示具体原因，不只显示“提交失败”。
- 非必填字段无值时统一显示“—”；不能以空字符串、`0` 或“未知日期”代替空值。
- 字段来自网页解析或公开信息时，应能够查看来源；无可追溯来源的数据不得标记为公开信息。
- 人工修改自动采集字段后，字段记录人工修改人和时间；后续自动采集结果作为新版本或差异记录，不静默覆盖人工值。
- 列表筛选、排序和导出使用同一字段口径；页面显示值不得与接口筛选值含义不一致。
- 业务枚举使用稳定编码保存、中文名称展示，后续修改展示文案不得改变历史数据含义。

## 7. 详细功能需求

## 7.1 登录与账号管理

### 7.1.1 用户故事

- 作为内部用户，我希望通过账号密码进入系统并只看到自己有权使用的功能。
- 作为申报负责人，我希望创建、停用账号并分配角色。

### 7.1.2 功能需求

| ID | P级 | 需求描述 | 验收标准 |
|---|---|---|---|
| AUTH-01 | P0 | 用户使用账号和密码登录 | 正确凭证进入政策中心；错误凭证不透露账号是否存在 |
| AUTH-02 | P0 | 连续错误登录受到限制 | 达到安全阈值后暂时限制继续尝试，并记录安全日志 |
| AUTH-03 | P0 | 负责人创建账号并分配角色 | 新账号可登录，菜单和操作权限符合角色 |
| AUTH-04 | P0 | 负责人启用或停用账号 | 停用账号不能登录，历史业务记录保留 |
| AUTH-05 | P0 | 负责人重置用户密码 | 重置后旧密码失效，新密码可登录 |
| AUTH-06 | P0 | 一个用户可同时成为项目对接人或项目成员 | 用户角色与项目角色可以同时存在，不相互覆盖 |
| AUTH-07 | P1 | 企业微信登录扩展 | 当前版本不实现，但账号模型允许后续绑定企业微信身份 |

### 7.1.3 账号列表字段业务规则

| 字段 | 类型 | 必填 | 校验与展示规则 | 数据来源 |
|---|---|---:|---|---|
| 登录账号 | 文本 | 是 | 4—50 个字符；仅允许字母、数字、下划线和短横线；全局唯一；创建后不允许普通编辑 | 负责人创建 |
| 用户姓名 | 文本 | 是 | 1—50 个字符；用于列表、项目人员和操作记录展示 | 负责人创建或编辑 |
| 业务角色 | 多值枚举 | 是 | 可选申报负责人、项目对接人、项目成员、产品规划团队；至少一个；首期申报负责人至少保留一个启用账号 | 负责人分配 |
| 账号状态 | 单值枚举 | 是 | 启用、停用；停用后不能登录，但历史项目和日志仍显示原姓名 | 负责人操作 |
| 最近登录时间 | 日期时间 | 否 | 登录成功时更新；从未登录显示“—” | 系统生成 |
| 创建时间 | 日期时间 | 是 | 创建成功时生成，不允许编辑 | 系统生成 |
| 创建人 | 关联对象 | 是 | 显示创建该账号的负责人姓名 | 系统记录当前操作人 |

### 7.1.4 规则与异常

- 不提供公开注册入口。
- 不直接删除已经关联项目或操作记录的用户，只允许停用。
- 密码必须使用安全哈希保存，任何页面和日志不得显示明文密码。

## 7.2 企业档案

### 7.2.1 用户故事

- 作为负责人，我希望统一维护公司级资料，并分别维护不同经营主体的资料，供政策评估使用。
- 作为普通用户，我希望查看政策评估所依赖的公司资料。

### 7.2.2 档案结构

| 层级 | 内容 |
|---|---|
| 企业共享档案 | 业务方向、技术能力、产品、人员、通用研发情况、行业描述 |
| 经营主体 | 主体名称、主体类型、统一社会信用代码、注册地、成立日期、法人属性 |
| 主体能力 | 资质、知识产权、研发数据、人员数据及其他申报相关材料 |

首期按北京适创科技有限公司、苏州数算软云科技有限公司、深圳适创腾扬科技有限公司三个经营主体建档。北京、苏州暂按独立法人初始化；深圳公开名称、官网展示和专利权利人记录与原“非独立分公司”假设冲突，主体类型必须在取得营业执照或国家企业信用信息公示结果后由负责人确认，开发不得写死。系统模型仍须同时兼容独立法人和非独立分支机构。

### 7.2.3 功能需求

| ID | P级 | 需求描述 | 验收标准 |
|---|---|---|---|
| ENT-01 | P0 | 展示企业共享档案和经营主体列表 | 用户可在一个页面查看共享资料及北京、苏州、深圳主体 |
| ENT-02 | P0 | 负责人编辑企业共享档案 | 保存后新评估使用最新资料，历史评估不被覆盖 |
| ENT-03 | P0 | 负责人独立编辑每个经营主体 | 编辑入口位于对应主体区域，不产生全局编辑歧义 |
| ENT-04 | P0 | 维护主体资质、知识产权和研发数据 | 各类信息可新增、编辑、停用或标记有效期 |
| ENT-05 | P0 | 研发投入比例在主体档案编辑中维护 | 页面不出现独立“编辑研发投入比例”按钮 |
| ENT-06 | P0 | 更新经营主体公开信息 | 操作只针对当前主体，完成后展示更新时间和公开来源 |

### 7.3.5 来源健康规则

| 状态 | 判定 |
|---|---|
| 正常 | 最近一次采集成功 |
| 偶发失败 | 最近一次失败，但连续失败次数小于 3 |
| 连续异常 | 连续 3 次及以上采集失败 |

### 7.6.4 当前结论定义

| 结论 | 使用场景 |
|---|---|
| 待确认 | 系统没有形成可用建议，需要负责人直接判断 |
| 建议申报 | 当前政策值得由指定主体推进申报 |
| 持续关注 | 有潜在机会，但当前时点或条件暂不适合立即申报 |
| 暂不建议申报 | 当前匹配度、成本或条件不足，不建议投入申报 |
| 无法判断 | 关键信息缺失，现阶段无法得出可靠结论 |
| 已转项目 | 建议申报政策已经生成项目 |
| 已归档 | 政策不再进入当前工作列表，但历史仍可查询 |

## 7.8 政策转项目

### 7.8.1 转换条件

- 当前结论为已确认的“建议申报”。
- 已指定主要申报主体。
- 政策尚未关联项目。
- 当前用户为申报负责人。

### 7.8.2 转换结果

系统创建项目并继承：

- 政策名称和政策 ID。
- 主要申报主体。
- 申报截止日期。
- 政策来源和评估结论。

负责人需要补充项目对接人，可选项目成员。新项目状态默认为“待申报”。

### 7.8.3 功能需求

| ID | P级 | 需求描述 | 验收标准 |
|---|---|---|---|
| CONV-01 | P0 | 校验转换条件 | 任一条件不满足时禁止转项目并说明原因 |
| CONV-02 | P0 | 创建唯一项目 | 转换成功后政策只关联一个项目 |
| CONV-03 | P0 | 继承政策与主体 | 项目详情能回溯政策并显示主要申报主体 |
| CONV-04 | P0 | 设置项目对接人 | 未选择对接人时不能完成项目创建 |
| CONV-05 | P0 | 政策状态更新 | 创建成功后政策显示“已转项目”并提供项目入口 |
| CONV-06 | P0 | 发送群通知 | 转项目成功后发送摘要和项目详情链接 |

## 7.9 项目台账与项目详情

### 7.9.1 项目状态

`待申报 → 已提交 → 成功 / 未通过 / 终止`

“申报准备”和“审核中”不作为项目状态，不得出现在状态筛选、状态修改或统计口径中。

允许的状态变化：

| 当前状态 | 可变更为 |

| 待申报 | 已提交、终止 |
| 已提交 | 成功、未通过、终止 |
| 成功 | 终态；负责人可通过更正操作修正错误并留痕 |
| 未通过 | 终态；负责人可通过更正操作修正错误并留痕 |
| 终止 | 终态；负责人可通过更正操作恢复并留痕 |

| LOG-03 | P0 | 查看通知记录 | 负责人可查看消息类型、发送时间、结果和重试次数 |

## 8. 状态模型

### 8.1 政策结论状态

| 状态 | 是否需要主体 | 可执行操作 |
|---|---:|---|
| 待确认 | 否 | 负责人选择结论 |
| 建议申报 | 是 | 确认后可转项目 |
| 持续关注 | 否 | 后续可重新评估或修改结论 |
| 暂不建议申报 | 否 | 后续可重新评估或归档 |
| 无法判断 | 否 | 补充资料后重新评估 |
| 已转项目 | 已绑定 | 查看关联项目 |
| 已归档 | 否 | 查看历史或由负责人恢复 |

结论还需保存确认属性：AI 建议、负责人已确认。该属性只控制样式和操作权限，不作为第二个并列状态展示。

### 8.2 项目状态

| 状态 | 说明 |
|---|---|
| 待申报 | 已建立项目，尚未完成正式提交 |
| 已提交 | 已向相关机构提交申报 |
| 成功 | 项目申报成功 |
| 未通过 | 已收到未通过结果 |
| 终止 | 因业务决定或外部原因停止推进 |

## 10. AI 评估产品要求

### 10.1 评估结构

1. 硬规则判断。
2. 加权评分。
3. DeepSeek 语义分析。
4. 多经营主体结果汇总。
5. 负责人最终确认。

### 10.2 输出要求

- 输出必须为系统可解析的结构化结果。
- 每项关键判断需要给出政策依据或企业档案依据。
- 明确区分“确定不符合”和“资料缺失无法判断”。
- 返回优势、风险、不满足项和缺失信息。
- AI 异常不得生成伪造结论。
- 模型名称、接口地址和参数配置化，不写死在业务代码中。

### 10.3 数据安全

- 只向 DeepSeek 提供公开资料和内部非保密资料。
- Demo 使用独立 API 密钥。
- 日志不得记录完整密钥。

## 14. MVP 验收用例

| 用例编号 | 验收场景 | 预期结果 |
|---|---|---|
| UAT-01 | 使用重点来源进行一次自动采集 | 成功生成任务记录、政策、原文和来源信息 |
| UAT-02 | 同一政策被重复发现 | 政策中心不出现重复记录 |
| UAT-03 | 已收录政策正文变化 | 形成新版本并重新评估，历史版本保留 |
| UAT-04 | 对一条政策评估三个经营主体 | 产生三份主体明细和一个汇总结论 |
| UAT-05 | AI 建议尚未确认 | 页面只显示一个弱化样式的当前结论 |
| UAT-06 | 负责人修改 AI 建议 | 当前结论更新，原因和修改历史可查询 |
| UAT-07 | 确认建议申报但未选主体 | 系统阻止确认并提示选择主要申报主体 |
| UAT-08 | 建议申报政策转项目 | 创建唯一项目，继承政策和主体，并发送通知 |

| UAT-10 | 对接人更新自己负责的项目 | 更新成功并形成状态历史 |
| UAT-11 | 对接人修改其他人的项目 | 页面和接口均拒绝操作 |
| UAT-12 | 来源连续三次失败 | 前两次只记录，第三次发送群提醒 |
| UAT-13 | 通知接口临时失败 | 自动重试，最终结果进入通知记录 |
| UAT-14 | 手机打开政策详情 | 页面正常展示，负责人可以确认结论 |
| UAT-15 | 手机打开项目编辑入口 | 不提供项目状态维护操作 |
| UAT-16 | 执行备份恢复演练 | 能恢复数据库、原始网页和附件 |

## 15. 实施顺序

采用“真实纵向闭环优先”，不先铺开全部来源：

1. 账号、企业档案、经营主体和来源基础能力。
2. 打通 1 个真实来源的采集、留痕、解析和政策入库。
3. 打通规则、DeepSeek、多主体评估和负责人确认。
4. 打通企业微信群通知和政策转项目。
5. 完成项目台账、项目权限和状态历史。
6. 扩展至 5 个重点来源。
7. 完成异常、备份、移动端和 UAT。

## 17. 业务假设

- 首期每天采集一次，优先保证 5 个重点来源。
- 所有用户可以查看全部政策和项目。
- 申报负责人首期为一人，并负责业务配置。
- 系统只处理公开信息和内部非保密资料。
- 项目只做轻量台账，不做材料或任务协作。
- Demo 服务器可短暂中断，重点保证数据可恢复。
- 自定义网址使用通用解析，但不保证所有网站均能自动采集。

## 18. 需求追踪与变更原则

- 本 PRD 中 P0 项目构成 MVP 验收范围。
- P1、P2 需求不得在未重新评估周期和资源的情况下进入 MVP。
- 新需求必须说明业务目标、用户角色、使用场景、数据来源、通知方式和流程影响。
- 状态、权限、数据关系或验收标准的变更必须同步更新 PRD、原型和测试用例。
- 完整产品与架构设计文档仍是技术边界和部署方案的上位参考。

## 19. PRD 评审关注项

以下规则是为了把已确认方案转化为可测试需求而增加的产品级细化，不扩大 MVP 范围；PRD 评审时应重点检查是否符合实际工作习惯：

1. 忘记密码由申报负责人重置，不建设短信或邮件找回密码。
2. 更新公开信息不得覆盖企业档案中的内部补充字段。
3. 负责人修改 AI 建议时填写修改说明，以支持审计追溯。
4. 项目进入已提交、成功、未通过或终止状态时，需要同时填写对应日期或说明。
5. 同一业务事件需要防止重复发送企业微信群通知。
6. 政策中心默认优先展示较新的政策，并支持按发布日期或截止日期调整顺序。
