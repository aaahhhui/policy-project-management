# Stage 3：政策转项目与项目台账设计

**日期：** 2026-08-03
**状态：** 已确认，待书面规格复核
**基线：** `main` at `4cd5cce`
**上游：** Stage 1 政策采集与留痕、Stage 2 评估决策闭环及流程优化

## 1. 目标

Stage 3 在不改变 Stage 2 人工政策结论语义的前提下，完成以下闭环：

```text
已确认建议申报 + 当前主申报企业
  -> 负责人转为唯一项目
  -> 项目台账与详情
  -> 对接人或负责人维护状态
  -> 状态、字段、操作者和历史可追溯
```

本阶段采用独立 `projects` 业务模块。政策的人工结论与项目生命周期分离：政策仍保留“建议申报”，是否已转项目由唯一关联项目派生，不把“已转项目”写入 `policies.current_conclusion`。

## 2. 范围

### 2.1 本阶段交付

- 校验政策转项目资格。
- 幂等、并发安全地为一条政策创建最多一个项目。
- 创建时绑定政策、当前主申报企业、申报负责人和项目对接人，可选项目成员。
- 项目列表、汇总、可转政策入口、搜索、组合筛选和服务端分页。
- 项目详情、普通字段维护、状态流转、受限更正和历史展示。
- 申报负责人、项目对接人、项目成员及其他已登录用户的权限边界。
- 项目状态历史、通用审计和越权写入审计。
- MySQL 迁移、自动化测试、Docker 验证和人工冒烟验收。

### 2.2 明确不交付

- 企业微信或其他外部通知，包括 `CONV-06`、`PROJ-11`、`PROJ-12`。
- 企业档案编辑。
- 新增政策来源和五来源覆盖率扩展。
- 备份恢复演练。
- 正式生产迁移。
- 账号管理扩展。
- 项目任务、申报材料、文件版本协作或项目删除。
- 通用工作流引擎、事件溯源系统或通知 Outbox。

Stage 3 只产生可供后续通知阶段识别的明确项目审计动作，不创建或发送通知任务。

## 3. 已确认的业务决策

1. 政策人工结论与转项目生命周期分离。转项目后，人工结论仍为“建议申报”，页面另行显示“已转项目”和项目入口。
2. 过期或截止日期未知的政策允许转项目；页面提示负责人复核，但不阻断创建。
3. 对接人和项目成员可选择任意启用账号，包括执行转项目的申报负责人本人。
4. 账号停用后保留已有关系和名称历史，但该账号不能继续写项目；负责人需更换对接人。
5. 申报负责人和当前项目对接人均可执行受限状态更正；对接人仅可更正自己负责的项目。
6. 更正原因非必填；填写时最长 1000 字符并进入历史和审计。
7. 结果说明非必填，填写时最长 500 字符。该规则覆盖 PRD `PROJ-13` 中结果说明必填的原约束。
8. 更正后清空与当前状态不再适用的当前字段，旧值保留在状态历史和审计中。

## 5. 数据模型

### 5.1 `projects`

| 字段 | 规则 |
|---|---|
| `id` | 主键 |
| `policy_id` | 非空、唯一外键；一条政策最多一个项目 |
| `name` | 1—300 字符；默认继承政策名称 |
| `primary_entity_decision_id` | 非空外键，指向创建时采用的当前主申报企业决策 |
| `primary_entity_seed_code` | 非空快照 |
| `primary_entity_legal_name` | 非空法定名称快照 |
| `applicant_owner_id` | 创建时执行转项目的申报负责人 |
| `applicant_owner_display_name` | 创建时名称快照 |
| `liaison_user_id` | 当前项目对接人，创建时必填 |
| `liaison_display_name` | 当前对接人名称快照 |
| `status` | `pending_application`、`submitted`、`succeeded`、`rejected`、`terminated` |
| `deadline_on` | 可空；默认继承政策截止日期 |
| `submitted_on` | 条件必填 |
| `result_on` | 条件必填 |
| `progress_note` | 可空，最长 2000 字符 |
| `result_note` | 可空，最长 500 字符 |
| `termination_note` | 进入终止时必填，最长 2000 字符 |
| `creation_idempotency_key` | 非空、唯一，保存创建请求幂等键 |
| `creation_request_fingerprint` | 非空，请求规范化后的摘要 |
| `version` | 非空递增整数，初始为 1，用于乐观并发控制 |
| `created_by` | 创建人 |
| `created_at`、`updated_at` | 服务端时间 |

项目保存创建依据快照，后续主企业决策变化不会静默改写项目。负责人如需修正主申报企业，必须走单独的项目字段更正并审计，不复用 Stage 2 的主企业切换作为隐式同步。

### 5.2 `project_members`

- `project_id` 与 `user_id` 组成唯一关系。
- 保存成员显示名快照和添加时间。
- 创建和后续维护只能选择启用账号。
- 成员在 Stage 3 仅用于展示，不获得项目写权限。

### 5.3 `project_status_history`

状态历史为追加式、不可编辑记录，至少保存：

- 项目、操作人 ID 和显示名快照。
- 操作类型：`created`、`transitioned`、`corrected`。
- 原状态与新状态；创建记录的原状态为空。
- 操作时间。
- 可选更正原因。
- 本次关联的提交日期或结果日期。
- 状态相关说明字段的前后快照。
- 操作前后项目版本号。

通用 `audit_events` 继续记录项目创建、普通字段更新、对接人和成员调整、主企业更正、状态操作及权限拒绝。专用状态历史表达业务过程，通用审计表达安全和字段变更，两者不互相替代。

## 6. 政策转项目

### 6.1 转换资格

服务端在创建事务内重新校验：

1. 政策当前人工结论已确认。
2. 当前结论为 `recommend_apply`。
3. 政策存在当前主申报企业决策。
4. 政策尚无项目。
5. 当前用户拥有 `applicant_owner` 角色。
6. 已选择启用的项目对接人。
7. 所有可选项目成员均为启用账号。

截止日期已过或未知不影响资格。服务端在创建预览和结果中返回复核警告。

### 6.2 创建结果

创建时：

- 项目名称默认继承政策名称，可由负责人修改。
- 绑定政策和创建时的当前主申报企业决策，并保存企业快照。
- 申报负责人默认为执行转换的用户。
- 项目对接人必填，项目成员可选。
- 截止日期默认继承政策截止日期。
- 初始状态固定为“待申报”。
- 同一事务写入创建状态历史、`project_created` 审计和政策侧 `policy_converted_to_project` 审计。

政策详情通过项目关系派生：

- `converted_to_project`
- `project_id`
- `project_name`

Stage 2 的当前结论、结论来源和确认时间均不改变。

### 6.3 幂等与唯一性

创建请求使用 `Idempotency-Key` 请求头。服务端保存键及规范化业务请求指纹：

- 相同键、相同政策和等价请求返回已有项目，不重复写历史或审计。
- 相同键但请求指纹不同，返回 `409 idempotency_key_reused`。
- 不同键再次转换同一政策，返回 `409 policy_already_converted`，并返回现有项目 ID。
- 数据库对 `projects.policy_id` 和 `creation_idempotency_key` 分别建立唯一约束，作为并发最终保证。

事务先锁定政策及当前主申报企业决策，再检查资格。唯一约束竞争失败后，服务端读取已存在记录并映射为稳定业务结果，不向前端暴露数据库异常。

## 7. 状态机与字段校验

### 7.1 正常流转

```text
待申报 -> 已提交 -> 成功
                  -> 未通过
待申报 ----------> 终止
已提交 ----------> 终止
```

“申报准备”和“审核中”不得进入数据库枚举、接口、筛选或统计。

正常流转校验：

- 新项目固定为“待申报”。
- 进入“已提交”时，提交日期必填且不得晚于服务端当前日期。
- 进入“成功”或“未通过”时：
  - 必须已有提交日期。
  - 结果日期必填，不得早于提交日期，也不得晚于服务端当前日期。
  - 结果说明非必填；填写时去除首尾空白后最长 500 字符。
- 进入“终止”时，终止说明去除首尾空白后必填，最长 2000 字符。
- 进展说明可空，最长 2000 字符。
- 项目名称去除首尾空白后为 1—300 字符。
- 截止日期早于项目创建日期只产生复核提示，不阻断保存。

### 7.2 受限更正

- “成功”或“未通过”可更正为“已提交”或另一结果状态。
- “终止”只能恢复到状态历史中最近一次进入终止前的状态。
- “成功”或“未通过”不允许直接更正为“待申报”。如果项目从“待申报”进入“终止”，则“终止”恢复到其真实前态“待申报”是唯一允许的例外；这不是任意选择目标状态。
- 申报负责人可更正全部项目。
- 当前项目对接人可更正自己负责的项目。
- 更正原因非必填；填写时去除首尾空白后最长 1000 字符。
- 结果状态更正回“已提交”时，清空当前结果日期和结果说明。
- “成功”与“未通过”互相更正时，重新校验结果日期；结果说明仍可为空。
- 从“终止”恢复时，清空当前终止说明。
- 被清空或替换的旧值保留在状态历史和通用审计中。

每次状态操作在一个事务中锁定项目、校验权限及预期版本、验证状态和字段、更新当前项目、追加状态历史和审计，然后返回新版本号。

## 8. 权限

所有已登录内部用户可查看全部项目列表和详情。Stage 3 不做部门或经营主体级数据隔离。

| 操作 | 申报负责人 | 当前项目对接人 | 项目成员/其他用户 |
|---|---:|---:|---:|
| 转项目 | 可 | 不可 | 不可 |
| 查看全部项目 | 可 | 可 | 可 |
| 修改名称、截止日期 | 可 | 不可 | 不可 |
| 更换对接人 | 可 | 不可 | 不可 |
| 增删成员 | 可 | 不可 | 不可 |
| 更正项目主申报企业 | 可，必须留痕 | 不可 | 不可 |
| 更新状态及关联日期 | 可 | 仅本人负责项目 | 不可 |
| 更新进展、结果、终止说明 | 可 | 仅本人负责项目 | 不可 |
| 执行受限状态更正 | 可 | 仅本人负责项目 | 不可 |

权限以当前用户角色和项目当前 `liaison_user_id` 为准：

- 任一当前拥有 `applicant_owner` 角色的用户可维护全部项目，不限于项目创建人。
- 对接人被更换后立即失去写权限，新对接人立即获得权限。
- 停用账号保留关系和名称历史，但不能登录或写项目。
- 前端根据接口返回的能力隐藏或禁用操作，后端仍对每个字段执行白名单校验。
- 对接人请求包含任何越权字段时整次拒绝，不静默忽略部分字段。
- 对已识别项目的越权写入返回 `403 project_write_forbidden`，并以独立短事务写入脱敏拒绝审计，避免随业务回滚丢失。

## 9. API 设计

### 9.1 读取接口

- `GET /api/projects/summary`
  - 返回总数、各状态数量和当前可转政策数量。
- `GET /api/projects`
  - 服务端分页。
  - 支持关键词、主申报企业、对接人、状态、截止日期范围和“我负责的”筛选。
  - 默认按 `updated_at DESC, id DESC` 稳定排序。
- `GET /api/projects/{project_id}`
  - 返回项目、政策、企业快照、成员、当前用户能力、状态历史和版本号。
- `GET /api/policies/convertible`
  - 仅申报负责人可用；服务端分页返回当前符合资格的政策。
- `GET /api/users/project-options`
  - 返回项目选择器所需的启用账号 ID、显示名和角色，不提供账号维护能力。

### 9.2 写接口

- `POST /api/policies/{policy_id}/project`
  - 要求 `Idempotency-Key`。
  - 请求包含项目名称、对接人 ID、成员 ID 列表和可选截止日期。
  - 完成资格复核、幂等创建、历史及审计写入。
- `PATCH /api/projects/{project_id}`
  - 请求包含 `expected_version` 和允许更新的普通字段。
  - 按角色字段白名单执行全有或全无更新。
- `POST /api/projects/{project_id}/primary-entity-corrections`
  - 仅申报负责人可用。
  - 请求包含 `expected_version`、目标主企业决策 ID 和可选更正原因。
  - 目标决策必须是该政策当前有效的主申报企业决策；不能任意选择历史企业或其他政策的决策。
  - 相同决策的等价重试返回当前项目，不重复审计；实际变更时更新项目企业快照并写入 `project_primary_entity_corrected`。
  - 更正原因非必填；填写时去除首尾空白后最长 1000 字符。
- `POST /api/projects/{project_id}/transitions`
  - 请求包含目标状态、`expected_version` 及目标状态所需日期和说明。
- `POST /api/projects/{project_id}/corrections`
  - 请求包含目标状态、`expected_version`、所需日期和可选原因。

所有请求模型禁止额外字段，避免拼写错误或越权字段被静默接受。

## 10. 项目台账与详情

### 10.1 项目台账 `/projects`

- 顶部展示项目总数和各状态汇总。
- 不展示状态图例或说明提示块。
- 汇总下方为文字按钮“`N 条政策可转项目`”；仅申报负责人可见。
- 点击后打开可转政策抽屉；选择政策进入创建表单。
- 创建表单预填项目名称、主申报企业和截止日期，要求选择对接人，可选成员。
- 截止日期已过或未知时显示醒目但非阻断提示。
- 列表支持名称关键词、主体、对接人、状态、截止日期和“我负责的”筛选。
- 使用服务端分页；筛选和页码保存在 URL 查询参数中，翻页和刷新后保持。
- 空状态区分“暂无项目”和“当前筛选无结果”。

### 10.2 项目详情 `/projects/:id`

按阅读和操作顺序展示：

1. 项目名称、当前状态和当前用户可执行操作。
2. 关联政策、原人工结论及政策详情入口。
3. 主申报企业、申报负责人、项目对接人和成员。
4. 截止、提交和结果日期。
5. 进展、结果和终止说明。
6. 状态历史。
7. 最近项目审计摘要。

政策详情增加独立的“已转项目”标识和项目入口。只有申报负责人且当前满足资格时显示“转为项目”。

项目转换和维护仅支持桌面端。移动宽度可只读查看项目，不显示转换、编辑、流转或更正入口。

## 11. 列表、筛选与分页语义

- 关键词匹配项目名称和关联政策名称。
- 主申报企业按快照编码精确筛选，显示法定名称。
- 对接人按当前用户 ID 精确筛选。
- 状态只允许五个业务状态。
- 截止日期支持起止范围，未知截止日期仅在未设置日期筛选时返回。
- “我负责的”表示当前用户等于项目当前对接人，不表示成员或创建人。
- 页码和每页数量均由服务端校验；默认每页 20 条，允许 10、20、50。
- 汇总数量按全量项目统计；可转政策数量按请求时的实时资格计算。
- 列表只返回展示和权限判断所需字段，详情和历史使用独立接口。

## 12. 并发与错误处理

### 12.1 乐观并发

项目普通更新、状态流转和更正必须携带 `expected_version`。服务端仅在当前版本匹配时更新并递增版本：

- 版本不一致返回 `409 project_version_conflict`。
- 响应包含当前版本和重新加载提示，不包含未授权字段。
- 冲突请求不产生部分更新、状态历史或成功审计。
- 服务端不自动合并或覆盖另一用户的修改。

### 12.2 稳定错误码

至少定义：

- `policy_not_convertible`
- `policy_already_converted`
- `primary_entity_missing`
- `project_liaison_required`
- `project_user_inactive`
- `project_write_forbidden`
- `project_transition_invalid`
- `project_correction_invalid`
- `project_field_validation_failed`
- `project_version_conflict`
- `idempotency_key_reused`

前端将已知错误映射为具体中文提示，未知错误显示通用提示。响应、应用日志和审计不得保存密码、Cookie、Authorization、密钥、完整请求头或内部异常正文。

## 13. 审计历史

审计动作至少包括：

- `project_created`
- `policy_converted_to_project`
- `project_updated`
- `project_liaison_changed`
- `project_members_changed`
- `project_primary_entity_corrected`
- `project_status_changed`
- `project_status_corrected`
- `project_write_denied`

成功审计保存对象、操作者、服务端时间、允许字段的前后摘要及可选原因。状态相关审计与专用状态历史在同一业务事务写入。权限拒绝审计只保存项目 ID、动作和标准拒绝码，不保存完整请求体。

列表和详情可展示项目专用状态历史及最近审计摘要；Stage 3 不建设全局审计管理页面。

## 14. 数据库迁移

新增 Alembic revision `0006_stage3_project_ledger`，revision 标识保持在 MySQL `alembic_version.version_num` 的既有长度限制内。

迁移内容：

- 创建 `projects`、`project_members`、`project_status_history`。
- 建立政策唯一关系、成员唯一关系、幂等键唯一约束和必要外键。
- 为状态、截止日期、对接人、主企业编码、更新时间及稳定分页建立索引。
- 外键限制删除；本阶段不提供政策、账号或项目物理删除。
- 不回填项目，不修改现有政策结论、评估、主企业决策或审计数据。

降级仅移除 Stage 3 新表、约束和索引，不改写 Stage 1/2 数据。开发验收在 MySQL 8.4 上执行 `upgrade head -> downgrade 0005_decision_timestamps -> upgrade head`，并确认既有 Stage 2 数据和接口保持可用。

本阶段不执行正式生产迁移。

### 15.3 Docker、MySQL 与人工验收
