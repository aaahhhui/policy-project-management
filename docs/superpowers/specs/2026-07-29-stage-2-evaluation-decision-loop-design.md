# 第二阶段：评估决策闭环设计

**日期：** 2026-07-29  
**状态：** 已确认  
**基线：** `feature/stage1-policy-ingestion-ai`

## 1. 目标

在第一阶段的政策采集、政策中心、三企业模拟评估和重评估能力之上，完成以下业务闭环：

```text
规则发布 -> DeepSeek 多企业评估 -> 人工复核与确认 -> 确定唯一主申报企业
```

本阶段不实现政策转项目、项目台账、企业微信通知、企业档案编辑和新增政策来源。

## 2. 角色与权限

- `applicant_owner`：创建规则草稿、编辑草稿、发布/停用规则、触发评估、修改 AI 建议、确认评估、选择或切换主申报企业。
- 其他已登录角色：查看已发布规则、评估结果、确认记录、主申报企业和历史批次，不允许修改。
- 所有写操作均记录操作者、时间、对象、动作及必要原因。

## 3. 评估规则

### 3.1 规则结构

规则集包含名称、说明和多个不可变版本。规则版本包含：

- 版本号和状态：`draft`、`published`、`retired`。
- 硬性条件：编码、名称、判断说明、是否启用。
- 评分条件：编码、名称、判断说明、权重、是否启用。
- 提示词版本。
- 创建人、发布人、创建时间和发布时间。

同一时刻仅允许一个已发布版本作为新评估的默认规则。已发布版本不得就地编辑；变更必须复制为下一版草稿。评分条件权重总和必须为 100。

### 3.2 版本绑定

创建评估批次时固定以下快照：

- 政策版本 ID。
- 企业档案快照。
- 规则版本 ID 和规则内容快照。
- 提示词版本、适配器和模型名称。

后续规则或企业资料变更不得改变历史评估。

## 4. DeepSeek 评估

### 4.1 适配器边界

保留现有 `EvaluationAdapter` 抽象，新增 DeepSeek 实现。服务端从环境变量读取 `DEEPSEEK_API_KEY`、Base URL、模型名、超时和重试次数；密钥不返回前端、不进入数据库和日志。

默认使用 DeepSeek 官方 OpenAI 兼容 `/chat/completions` 接口和 JSON Output。请求提示词明确要求 JSON，并提供输出样例；服务端用 Pydantic 严格验证最终结构。

### 4.2 输出结构

批次级输出：

- 政策摘要。
- 关键申报条件。
- 总体建议结论。

企业级输出：

- 匹配等级：`high`、`medium`、`low`、`uncertain`。
- 0–100 综合分数。
- 硬性条件逐项结果与依据。
- 评分条件逐项得分与依据。
- 匹配依据、未满足条件、风险和建议动作。

### 4.3 异常与重试

- 429、500、503、连接超时及偶发空内容：指数退避后有限重试。
- 400、401、402、422：不重试，记录经过脱敏的失败类型。
- JSON 解析或业务结构校验失败：允许一次纠正重试，仍失败则批次标记 `failed`。
- 一个批次只有在三家企业结果全部通过校验后才原子提交；不得保存部分成功结果。
- 保存模型名、请求 ID、开始/结束时间、重试次数及 Token 用量，禁止保存 API Key 和授权头。

## 5. 人工复核与确认

评估批次状态扩展为：

```text
pending -> running -> awaiting_confirmation -> confirmed
                    -> failed
```

DeepSeek 成功生成结果后进入 `awaiting_confirmation`。负责人可逐企业接受或修改 AI 建议；修改任一字段时必须填写修改原因。确认时保存独立的人工最终值，不覆盖 AI 原始结果。

确认操作具有幂等性：同一批次重复提交相同确认返回现有结果；已确认批次不可再次编辑。重新评估始终创建新批次并保留历史。

## 6. 主申报企业

- 只能从当前已确认批次的三家候选企业中选择。
- 每项政策同一时刻最多一个主申报企业。
- 选择记录关联政策、确认批次、企业、操作者、原因和时间。
- 首次选择原因可选；切换企业时原因必填。
- 页面分别展示“AI 推荐”和“人工确定”，不得将 AI 推荐自动写成主申报企业。
- 历史选择保留，当前记录通过唯一约束和事务锁保证一致性。

## 7. 页面与接口

### 7.1 规则页面

- `/evaluation-rules`：规则列表、当前发布版本、状态和更新时间。
- `/evaluation-rules/:id`：版本历史、规则内容、创建新草稿、编辑、发布和停用。

### 7.2 政策详情页

- 展示当前评估使用的规则版本、模型、状态和失败原因。
- 企业卡片同时展示 AI 原始结果和人工最终结果。
- 待确认批次提供复核表单；字段发生修改时显示原因必填。
- 已确认后提供主申报企业选择；切换时要求原因。
- 历史批次和历史主申报选择只读。

## 8. 审计

新增通用审计事件，至少覆盖：

- `evaluation_rule_draft_created`
- `evaluation_rule_draft_updated`
- `evaluation_rule_published`
- `evaluation_rule_retired`
- `evaluation_started`
- `evaluation_failed`
- `evaluation_confirmed`
- `primary_entity_selected`
- `primary_entity_changed`

事件保存对象类型、对象 ID、操作者、动作、原因、时间和脱敏后的变更摘要。

## 9. 验收标准

1. 负责人可发布版本化规则；历史评估固定引用原规则版本。
2. 真实 DeepSeek 可基于政策、三家企业档案和规则生成合法结构化结果。
3. API 异常、空结果和非法结构不会产生半成品结果，且按策略重试或失败。
4. 人工修改 AI 建议时未填写原因不能提交。
5. 已确认批次同时保留 AI 原始值和人工最终值，且不可再次编辑。
6. 每项政策最多一家主申报企业，切换企业必须填写原因。
7. 规则、评估、确认和主企业选择的写操作均可审计。
8. 后端单元/集成测试、前端组件测试、类型检查、生产构建和端到端测试通过。
9. 使用真实 API Key 完成至少一项政策、三家企业的一次真实评估冒烟测试，并确认日志无密钥泄漏。

## 10. 非目标

- 不创建项目，不建设项目台账或项目状态流转。
- 不发送企业微信或其他外部通知。
- 不扩展账号管理、企业档案编辑或更多政策来源。
- 不引入通用工作流引擎或多模型供应商自动切换。
