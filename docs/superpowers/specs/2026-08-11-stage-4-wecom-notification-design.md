# Stage 4：企业微信群机器人通知闭环设计

**日期：** 2026-08-11
**状态：** 已完成交互确认，待书面规格复核
**基线：** `main` 合并提交 `57fb3e6`，Stage 4 规划启动提交 `d0758e6`
**上游：** Stage 1 政策采集、Stage 2 评估决策、Stage 3 政策转项目与项目台账

## 1. 目标

Stage 4 在不阻塞现有业务事务、不引入消息中间件的前提下，完成以下闭环：

```text
业务事件与业务数据同事务落库
  -> 唯一通知记录成为事务型 Outbox
  -> notifier worker 异步领取
  -> 企业微信群机器人发送
  -> 成功或可读失败结果留痕
  -> 有限自动重试
  -> 负责人查看记录并可手动重发最终失败项
```

本阶段满足 `CONV-06`、`PROJ-11`、`PROJ-12`，并纳入既有 P0 的高匹配政策、评估完成和来源连续异常通知。企业微信只承担摘要分发和详情入口，不承担登录、授权或复杂业务操作。

## 2. 范围

### 2.1 本阶段交付

- 企业微信群机器人单群 Webhook 适配器。
- 通知记录作为事务型 Outbox，与业务状态原子写入。
- 独立 notifier worker、并发领取、领取令牌和超时回收。
- 首次发送、三次自动退避重试和最终失败后的负责人手动重发。
- 同一业务事件唯一记录及本地幂等成功语义。
- 通知记录、追加式发送尝试历史和可读失败摘要。
- 负责人专用通知记录页面、筛选、分页、详情和手动重发。
- 政策或项目详情链接，以及登录后安全回跳。
- 企业微信内置浏览器中的真实手机验收。
- 通知读取、重发、Webhook、日志和链接相关的权限与安全测试。
- 评估规则版本的高匹配分数阈值，既有值默认初始化为 80。
- 来源连续失败段的最小健康状态及通知触发。

### 2.2 通知场景

本阶段覆盖六类业务场景：

1. 高匹配政策或评估结果变更。
2. 政策评估完成。
3. 政策转项目。
4. 项目首次进入已提交。
5. 项目首次进入成功。
6. 来源连续异常。

同一评估批次不会同时发送“高匹配政策”和“评估完成”两条消息。达到阈值时展示为“高匹配政策”；未达到阈值的首次评估展示为“评估完成”；后续发生实质变化但新结果不属于高匹配时展示为“评估结果变更”。

### 2.3 明确不交付

- 企业微信登录、自建应用、个人定向通知或群内交互操作。
- 企业档案编辑。
- 新增政策来源或五来源覆盖率扩展。
- 备份失败通知和备份恢复演练。
- 正式生产迁移。
- Redis、Kafka、通用工作流、通用事件总线或微服务拆分。
- 项目任务、申报材料或文件版本协作。
- 对 Stage 4 启用前的历史事件补发通知。

## 3. 已确认的业务决策

1. 使用单个企业微信群机器人 Webhook，通过服务端环境配置注入。
2. 高匹配与评估完成采用互斥展示语义，同一评估批次只产生一条通知。
3. 首次可用评估必发；后续仅在汇总结论、高匹配状态或任一经营主体匹配等级变化时发送。
4. 高匹配由规则版本中的 `high_match_score_threshold` 判定，范围为 0—100，默认值为 80。
5. 自动发送最多四次：首次、1 分钟后、5 分钟后、30 分钟后。
6. 最终失败后，申报负责人可以手动重发同一通知。
7. 用户未登录时，登录成功后必须安全回到消息指向的站内详情。
8. 来源异常按连续失败段通知一次：第 3 次触发，第 4 次及以后不重复，成功后重置。
9. `failed` 和 `partial_failed` 均计入来源连续失败；只有 `succeeded` 重置。
10. 项目“首次已提交”和“首次成功”按项目整个生命周期各通知一次，状态更正后再次进入不重复。
11. Stage 4 启用前的历史项目、评估和采集任务不补发；UAT 使用新测试事件。

## 5. 数据模型

### 5.1 `notification_deliveries`

每个业务事件最多一行：

| 字段 | 规则 |
|---|---|
| `id` | 主键 |
| `event_key` | 非空、唯一、稳定的业务事件键 |
| `event_type` | 稳定事件类型代码 |
| `display_type` | 高匹配政策、评估完成、评估结果变更、政策转项目、项目已提交、项目成功、来源异常 |
| `object_type`、`object_id` | 政策、项目或来源的关联对象 |
| `object_name_snapshot` | 触发时名称快照 |
| `detail_path` | 经过白名单约束的站内相对路径，不保存完整域名 |
| `message_snapshot` | 发送所需的最小安全结构化摘要，不含密钥或原始异常 |
| `triggered_at` | 业务事件发生的服务端时间 |
| `status` | `pending`、`sending`、`retry_wait`、`succeeded`、`failed` |
| `attempt_count` | 已开始的总尝试次数，非负整数 |
| `send_round` | 发送轮次，初始为 1；每次有效手动重发递增 |
| `round_attempt_count` | 当前轮次已开始的尝试次数，用于计算退避位置 |
| `next_attempt_at` | 自动重试时间；非等待状态为空 |
| `sent_at` | 首次成功时间；未成功为空且成功后不可改写 |
| `last_error_code` | 稳定、脱敏错误码 |
| `last_failure_summary` | 可读中文摘要，不含内部异常正文 |
| `claim_token`、`claimed_at` | 并发领取和超时恢复字段 |
| `version` | 手动重发和条件更新的乐观版本 |
| `created_at`、`updated_at` | 服务端时间 |

`event_key` 示例：

- `project:{project_id}:created`
- `project:{project_id}:first_submitted`
- `project:{project_id}:first_succeeded`
- `evaluation:{policy_id}:batch:{batch_id}:material_change`
- `source:{source_id}:failure_episode:{episode_started_task_id}`

普通列表不展示 `event_key`；详情也无需向用户暴露内部结构。

### 5.2 `notification_attempts`

发送尝试为追加式记录，不可编辑：

- 通知 ID 和该通知内递增的尝试编号。
- 触发方式：`initial`、`automatic_retry`、`manual_retry`。
- 开始、结束服务端时间。
- 结果：成功、可重试失败、永久失败、结果不确定。
- 可选 HTTP 状态、稳定提供方错误码和中文失败摘要。
- 不保存请求 URL、请求头、消息请求体、完整响应或异常正文。

### 5.3 `source_health_states`

每个来源最多一行运行状态：

- `source_id` 作为唯一关系。
- `consecutive_failure_count`。
- `episode_started_task_id`。
- `last_processed_task_id`，防止同一任务重复计数。
- `updated_at`。

来源展示状态由来源启停和连续次数派生：停用、正常、偶发失败或连续异常。通知是否已产生由该失败段稳定事件键及通知唯一约束决定，不另存可漂移的“已通知”布尔值。

## 6. 事务、并发与幂等

### 6.1 事务内入队

业务服务在完成自己的状态校验和数据变更后、提交前调用通知事件接口。业务数据、现有历史或审计以及通知记录使用同一 SQLAlchemy Session：

- 业务事务回滚时，通知记录一并回滚。
- 通知唯一冲突按等价事件处理，不破坏业务成功。
- 不允许业务提交成功后再通过进程内回调补建通知，避免进程退出造成永久遗漏。
- 不允许在业务事务内调用企业微信。

### 6.2 worker 领取

worker 使用 `SELECT ... FOR UPDATE SKIP LOCKED` 按 `next_attempt_at`、创建时间和 ID 稳定领取一条可发送记录，写入 `sending`、claim token、领取时间和尝试记录后提交。外部调用结束后，新事务只有在状态和 claim token 仍匹配时才能写入结果。

超过领取时限的 `sending` 记录视为结果不确定，由 worker 回收并进入下一次可用重试；旧 worker 的迟到结果因 claim token 不匹配而不得覆盖新状态。

### 6.3 成功语义

数据库唯一约束保证同一事件只有一条通知记录。成功落库后，自动领取和手动重发均不得再次调用渠道；等价操作返回已有成功结果。

企业微信群机器人 Webhook 不提供本系统业务事件的幂等能力，因此无法完全消除以下崩溃窗口：企业微信已经接受消息，但 worker 在本地提交成功前退出。Stage 4 明确采用“至少一次外部投递 + 本地幂等成功”语义：结果不确定时优先重试，极端情况下群内可能重复；不允许发送前预先标记成功，因为那会造成永久漏通知。

## 7. 通知触发规则

### 7.1 评估完成与实质变化

评估批次的三经营主体结果全部通过校验，并在同一事务转为 `awaiting_confirmation` 时进行判定。“可用评估”指已经完整保存结构化结果且状态为 `awaiting_confirmation` 或 `confirmed` 的批次；`pending`、`running`、`failed` 和 `cancelled` 均不参与比较。

高匹配状态为：任一主体存在有效 `score`，且分数大于或等于该批次规则快照中的 `high_match_score_threshold`。没有有效分数时不判定为高匹配。阈值随规则版本快照固化，后续规则修改不重写历史判断。

- 首次可用评估必生成通知。
- 后续批次与该政策最近一次更早的可用评估比较。
- 实质变化仅包括：汇总结论变化、高匹配布尔值变化、任一相同经营主体的 `match_level` 变化，或者经营主体集合发生变化。
- 分数变化但未跨阈值、依据、风险、建议动作和自然语言摘要变化均不触发。
- 失败、取消、负责人确认、人工结论调整或主申报企业选择不触发评估通知。

新批次为高匹配时展示为“高匹配政策”；首次且非高匹配时展示为“评估完成”；后续有实质变化但非高匹配时展示为“评估结果变更”。消息安全快照保存关键前后值，不保存 AI 原始响应。

### 7.2 政策转项目

项目创建、创建状态历史、`project_created`、`policy_converted_to_project` 和 `project:{id}:created` 通知记录在同一事务写入。消息包含项目名称、主申报企业、对接人、截止日期和项目详情入口。

项目创建幂等重试、不同键竞争及并发唯一约束收口均不得产生第二条通知。

### 7.3 项目首次已提交和首次成功

正常流转与受限更正共用同一触发函数：

- 项目生命周期首次进入 `submitted` 时写入 `project:{id}:first_submitted`。
- 项目生命周期首次进入 `succeeded` 时写入 `project:{id}:first_succeeded`。
- 离开后再次进入相同状态不通知。
- 是否首次由事件键唯一性判断，不依赖当前状态或可被更正的普通字段。

已提交消息包含提交日期；成功消息包含结果日期和经长度限制的结果说明。业务事务失败或版本冲突不留下通知。

### 7.4 来源连续异常

采集任务收口事务锁定对应 `source_health_states`：

- `failed` 和 `partial_failed` 使连续次数加一。
- `succeeded` 清零次数和失败段起始任务。
- 其他中间状态不更新健康状态。
- 新失败段第一次失败时保存 `episode_started_task_id`。
- 第 3 次失败写入该失败段唯一通知；第 4 次及以后不重复。
- 成功后下一次失败开启新失败段，之后再次连续 3 次可生成新通知。
- `last_processed_task_id` 保证任务收口的等价重试不重复累计。

消息包含来源名称、连续失败次数、最近任务编号、标准化失败摘要和负责人可访问的来源或通知记录入口。

## 8. 消息格式与详情链接

群消息采用受控 Markdown 模板。每条消息包括：

- 明确的业务标题。
- 对象名称和必要事实摘要。
- 事件发生时间。
- 一个主要详情入口。

政策消息链接至 `/policies/{id}`，项目消息链接至 `/projects/{id}`，来源异常链接至对应通知记录或来源记录。链接完整基址由可信服务端环境配置拼接，数据库只保存相对路径。

消息不得包含 Webhook、登录凭据、Cookie、Authorization、AI 原始输出、内部异常正文、完整审计载荷或超出当前内部用户可见范围的数据。

## 9. 发送、重试与失败摘要

### 9.1 成功判定

只有 HTTP 调用成功、响应可以安全解析并明确表示企业微信接受成功，才标记 `succeeded` 和首次 `sent_at`。仅有 HTTP 2xx 但响应畸形或业务结果不明确时，不得标记成功。

### 9.2 自动重试

可重试错误最多尝试四次：

1. 首次立即发送。
2. 1 分钟后自动重试。
3. 5 分钟后自动重试。
4. 30 分钟后自动重试。

网络超时、连接失败、限流、渠道服务端错误和无法确认结果的响应属于可重试错误。缺少配置、Webhook 格式非法或渠道明确返回永久拒绝属于永久错误，直接进入最终 `failed`，不消耗无意义的后续自动尝试。

### 9.3 手动重发

只有申报负责人可以对最终失败记录执行手动重发。请求必须携带 `expected_version`：

- 当前仍为 `failed` 且从未成功时，状态改回 `pending`，保留原尝试历史并追加手动重发审计。
- 有效重发同时递增 `send_round`，并将 `round_attempt_count` 归零；`attempt_count` 继续累计，不覆盖历史。
- 已被其他操作重启时返回当前状态，不重复排队。
- 已成功时返回已有结果，不调用渠道。
- 越权写入返回 403，并以独立短事务记录脱敏的 `notification_retry_denied`。

手动重发开启新的“首次 + 最多三次自动重试”发送轮次，但不创建新的通知记录或事件键。

### 9.4 可读失败摘要

通知记录和页面只使用稳定错误码及中文摘要，例如：

- `wecom_connection_timeout`：连接企业微信超时，将按计划重试。
- `wecom_rate_limited`：发送频率受限，将按计划重试。
- `wecom_configuration_missing`：机器人未配置，请检查服务端配置。
- `wecom_webhook_rejected`：机器人配置无效或已失效，请检查服务端配置。
- `wecom_response_invalid`：企业微信返回无法确认的结果，将按计划重试。

未知异常统一映射为安全摘要；不得保存 `str(error)`、响应正文或内部堆栈。

## 10. API 与权限

### 10.1 读取接口

- `GET /api/notifications`
  - 仅申报负责人。
  - 按通知类型、状态和触发时间范围筛选。
  - 服务端分页，默认按 `triggered_at DESC, id DESC` 稳定排序。
- `GET /api/notifications/{notification_id}`
  - 仅申报负责人。
  - 返回安全消息快照和按尝试编号排序的尝试历史。

### 10.2 写接口

- `POST /api/notifications/{notification_id}/retry`
  - 仅申报负责人。
  - 请求只包含 `expected_version`，禁止额外字段。
  - 只允许对最终失败且从未成功的记录重启。

不提供前端或外部调用者可以任意指定消息内容、Webhook 或目标群的发送接口。

所有底层业务详情继续按既有权限读取。Stage 4 不改变“所有已登录内部用户可查看全部政策和项目”的规则；通知记录与重发操作则只对申报负责人开放。

## 11. 通知记录页面

新增负责人专用 `/notifications`，主导航只对申报负责人显示入口。

列表展示：

- 通知类型和业务对象。
- 触发时间和发送状态。
- 首次成功时间。
- 尝试次数。
- 最后失败摘要。

页面支持通知类型、状态、触发时间筛选和服务端分页。空状态区分“尚无通知”和“当前筛选无结果”。

详情展示安全消息快照与追加式尝试历史。只有最终失败时显示“重新发送”；等待、发送、重试等待和成功状态均不显示可执行按钮。并发版本冲突提示用户刷新当前记录。

通知记录管理定位为桌面操作，移动宽度不提供手动重发入口。

## 12. 登录回跳与移动端

从群消息进入政策或项目详情时：

- 已登录用户直接进入目标详情。
- 未登录用户进入账号密码登录页，并携带原站内相对路径。
- 登录成功后回到正确详情，不进入默认首页。
- 回跳目标只接受白名单内的相对政策、项目、来源或通知路径。
- 绝对 URL、协议相对 URL、登录页循环、服务不可用页循环及无法识别的目标回退到工作台，防止开放重定向。

不接入企业微信身份。项目详情在移动端继续只读，隐藏转换、编辑、流转和更正控件；政策详情保持既有移动端阅读和负责人确认能力。

## 13. Webhook 与日志安全

- Webhook 仅通过服务端环境变量或部署秘密配置注入，不写入代码、数据库、前端构建产物、文档实例值或 Git。
- 发送前校验 HTTPS、允许的企业微信域名和固定机器人路径。
- 日志层统一对 URL 查询参数、Authorization、Cookie 和代表性密钥形态脱敏。
- 适配器不得记录完整请求 URL、请求头、消息请求体或完整响应。
- 通知记录、尝试记录、审计和 API 响应不保存 Webhook 或 `key` 参数。
- 详情链接由可信公开基址与白名单相对路径组成，不接受业务数据提供完整外部 URL。
- 配置缺失不拖垮业务 API；通知事件仍可落库并显示安全的配置失败摘要。

## 14. 审计

通知自动投递过程由通知记录和尝试历史表达，不为每次 worker 轮询制造通用审计噪声。通用审计至少增加：

- `notification_manual_retry_requested`
- `notification_retry_denied`

成功的手动重发请求保存操作者、通知 ID、原状态、新状态和版本，不保存消息正文或配置。拒绝审计只保存通知 ID、动作和稳定拒绝码，以独立短事务提交，避免随失败请求回滚。

项目、评估和来源的现有业务审计继续保留，通知记录可通过业务对象和触发时间与其关联，但不得依赖审计扫描来创建通知。

## 15. 数据库迁移

新增 Alembic revision `0008_stage4_notifications`：

- 创建 `notification_deliveries`、`notification_attempts` 和 `source_health_states`。
- 为事件键、状态与下次尝试时间、稳定分页、业务对象和尝试顺序建立必要唯一约束及索引。
- 在评估规则版本增加 `high_match_score_threshold`，范围约束为 0—100，既有及新记录默认初始化为 80。
- 不回填历史通知，不修改 Stage 1–3 业务事实、项目状态、人工政策结论或历史审计。

降级移除 Stage 4 新表、索引、约束和阈值字段，不改写 Stage 1–3 数据。MySQL 8.4 必须验证 `upgrade head -> downgrade 0007_reconcile_eval_constraint -> upgrade head`，以及 fresh upgrade 和既有升级库兼容。

本阶段不执行正式生产迁移。

## 16. 测试策略

实施计划必须严格采用 TDD：每个任务先写目标明确的失败测试，确认失败原因，再实现最小代码；目标测试通过后运行相关回归并频繁提交。

### 16.1 后端领域与接口

- 六类触发场景和所有不触发分支。
- 评估首次通知、三项实质变化、主体集合变化、阈值跨越和非实质变化。
- 阈值范围、默认 80、规则版本不可变和快照固化。
- 项目创建幂等、并发竞争、状态更正及生命周期首次通知。
- 来源 `failed`、`partial_failed`、`succeeded`、连续段重置和任务等价收口。
- 业务事务回滚不留下通知，通知唯一冲突不破坏业务。
- 列表筛选、稳定排序、分页、详情和安全序列化。
- 负责人读取与重发、其他角色 403、重发版本冲突和拒绝审计。

### 16.2 worker 与适配器

- 并发 `SKIP LOCKED` 领取和 claim token。
- 外部调用发生在数据库事务外。
- 迟到结果不能覆盖新 claim。
- 超时领取回收和结果不确定重试。
- 首次、1 分钟、5 分钟、30 分钟的退避计划。
- 可重试与永久错误分类。
- HTTP 成功但业务失败、畸形响应、限流、超时和连接失败。
- 最终失败手动重发、保留历史、成功后不再发送。

### 16.3 安全与权限

- 使用代表性 Webhook 和密钥形态注入配置、异常和渠道响应。
- 数据库、API、审计、前端、测试日志和容器日志均不得出现完整秘密。
- Webhook HTTPS、域名和路径校验。
- 恶意响应正文和异常文本被映射为稳定摘要。
- 登录回跳拒绝绝对 URL、协议相对 URL、未知路径和循环目标。
- 非负责人无法读取通知记录或调用重发；前端隐藏不替代后端权限。

### 16.4 前端

- 负责人导航入口和其他角色隐藏。
- 类型、状态、时间筛选，URL 条件保持和服务端分页。
- 加载、空状态、失败状态和安全错误提示。
- 详情快照、尝试历史和按钮状态。
- 手动重发成功、失败和版本冲突。
- 登录后安全回跳。
- 移动端项目只读及通知手动重发入口隐藏。

### 16.5 Docker、MySQL 与真实 UAT

1. 后端测试、Ruff、mypy、前端测试、Vue TypeScript 和 Vite 生产构建通过。
2. Docker Compose fresh build 后 MySQL、API、web、collector、evaluator、scheduler 和 notifier 达到健康基线。
3. MySQL 验证迁移往返、事件唯一约束、并发领取、项目并发触发和来源任务等价收口。
4. 使用真实测试 Webhook 在企业微信群发送政策和项目消息。
5. 在真实企业微信手机端内置浏览器点击消息；普通 Chromium 移动视口只能预检，不能替代。
6. 未登录时显示账号密码登录页，登录后到正确政策或项目详情；已登录时直接进入。
7. 验证政策内容可读，项目详情只读且没有维护、更正或转换控件。
8. 验证返回、刷新、会话过期和对象不存在提示。
9. 扫描页面地址、数据库、API 响应、审计载荷、Git 跟踪文件和全部 Compose 服务日志，确认 Webhook、Authorization、Cookie、私钥及代表性 API key 均为零泄漏。

真实 UAT 前置输入仅包括：测试群 Webhook、手机可访问的 HTTPS Demo 地址和专用测试账号。这些值只进入本地秘密配置，不写入规格或验收记录正文。

## 18. 变更控制

本规格确认后，任何改变通知场景、评估实质变化口径、高匹配阈值、事件键、成功语义、重试次数、权限、消息内容、移动端边界或验收范围的需求，都必须先更新本规格和相应测试用例。

企业微信登录或自建应用、企业档案编辑、新来源或五来源扩展、备份失败通知、备份恢复演练和正式生产迁移不得在 Stage 4 实现过程中顺带加入。
