# 采集频道编排修复设计

## 背景

真实采集任务 1 在访问广东省工业和信息化厅网站前失败。采集工作进程只向 `gdii` Spider 传入了任务 ID 和 90 天截止日期，没有传入 Spider 必需的频道 ID 和列表地址。

## 目标

一个采集任务必须遍历其来源下所有启用频道。每个频道单独启动一次 Spider，并传入：

- `task_id`
- `channel_id`
- `list_url`
- `cutoff_date`

禁用频道不得启动。所有频道运行结束后，任务根据已持久化的采集明细和所有 Spider 退出码汇总为成功、部分失败或失败。

## 设计

`workers.collector.run_once` 在领取任务后加载任务对应的来源及其频道，筛选启用频道，并按频道 ID 稳定排序。工作进程为每个频道构造独立的 Scrapy 命令并顺序执行，避免多个 Spider 并发写入同一任务时引入新的事务和文件竞争。

若所有 Spider 均以退出码 0 结束，向现有 `finish_from_items` 传入 0；任一 Spider 非零退出，则传入非零结果。现有任务汇总规则继续依据采集明细判断成功或部分失败，不修改数据模型和 API。

如果来源没有启用频道，任务以失败结束并记录非零采集结果，不启动 Spider。

## 测试

单元回归测试覆盖：

1. 两个启用频道产生两条 Scrapy 命令。
2. 每条命令包含正确的任务 ID、频道 ID、列表地址和截止日期。
3. 禁用频道不产生命令。
4. 任一频道失败时，传给任务汇总的进程结果为非零。
5. 没有启用频道时任务失败。

实现后运行完整后端测试，重建采集容器，再触发一次真实采样并记录任务终态与两个频道的采集结果。

## 非目标

- 不修改 GDII 页面解析规则。
- 不改变采集任务、频道或政策的数据模型。
- 不增加并行采集。
- 不调整前端页面。
