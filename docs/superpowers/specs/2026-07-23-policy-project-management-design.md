# 政府科创政策收集与项目申报管理系统

## MVP 产品与架构设计文档

- 文档日期：2026-07-23
- 文档状态：产品与架构方案已确认，等待进入实施计划
- 项目阶段：Demo 验证级 MVP
- 目标周期：2—3 周完成可上线验证版本

## 1. 结论摘要

本产品是一套面向公司内部团队的政策收集、政策评估和项目申报管理系统。首期围绕 5 个重点政策来源建立一条真实可运行的业务闭环：自动发现政策、保留原文证据、结合多个经营主体进行结构化评估、由负责人确认唯一结论、发送企业微信群通知，并将建议申报的政策转为项目台账。

系统采用“模块化单体业务应用 + 独立爬虫运行区”的架构。前端使用 Vue 3，业务后台使用 FastAPI，爬虫使用 Scrapy、scrapy-playwright 和 Scrapyd，数据保存于 MySQL 8.4，AI 评估调用 DeepSeek API。Demo 部署在个人腾讯云账号的中国香港 Lighthouse 轻量应用服务器，正式上线前迁移至公司企业账号。

## 2. 产品愿景与目标

### 2.1 一句话愿景

让公司从分散、人工、不可追溯的政策收集方式，升级为及时、可评估、可确认、可转项目的内部政策与申报管理闭环。

### 2.2 业务目标

1. 降低政策负责人每周收集、筛选和整理政策的人工投入。
2. 保证重点政策来源能够稳定覆盖，并在合理时间内同步到团队。
3. 基于公司及多个经营主体的资料形成一致、可解释的评估结果。
4. 让申报项目的当前进度、负责人和结果可视化、可追溯。

### 2.3 MVP 成功指标

| 指标 | 目标 |
|---|---:|
| 5 个重点来源采集覆盖率 | ≥ 90% |
| 政策发布至系统入库时间 | ≤ 24 小时 |
| 政策来源可追溯率 | 100% |
| 政策负责人每周人工投入 | 从 2—5 小时降至 1—2 小时 |
| 关键状态修改可追溯率 | 100% |

## 3. 用户与职责

系统不设置“系统管理员”业务角色。首期预计 5—15 名内部用户，所有用户均可查看全部政策和项目。

| 用户角色 | 核心诉求 | 主要职责 |
|---|---|---|
| 申报负责人 | 快速发现值得申报的政策并统一推进 | 维护业务配置、确认政策结论、指定申报主体、政策转项目、管理全部项目 |
| 项目对接人 | 掌握并更新自己负责项目的进度 | 更新自己负责项目的状态、日期、结果和说明 |
| 项目成员 | 了解政策依据和项目进展 | 查看政策、评估明细和项目状态 |
| 产品规划团队 | 从政策中识别方向和机会 | 查看政策、评估依据和项目结果 |

账号和角色由申报负责人维护。首期采用账号密码登录，保留后续接入企业微信登录的扩展能力。

## 4. 产品范围与优先级

### 4.1 P0：MVP 必须交付

- 账号密码登录与角色权限。
- 企业共享档案和多经营主体档案。
- 政策来源配置、启停、采集频率和健康状态。
- 5 个重点来源的自动采集。
- 自定义来源网址和单条政策链接录入。
- 政策解析、去重、原文与附件留痕。
- 硬规则、加权评分和 DeepSeek 语义分析组成的政策评估。
- 多经营主体分别评估，汇总为政策的一个当前结论。
- 负责人确认或修改结论，并在建议申报时指定主要申报主体。
- 企业微信群机器人业务通知和连续异常通知。
- 一条政策最多转为一个项目。
- 项目台账、项目详情和项目状态历史。
- 关键操作、通知、采集和评估任务日志。
- 每日异地备份并保留 7 天。

### 4.2 P1：MVP 后增强

- 一条政策生成多个申报项目。
- Redis 或独立消息队列。
- 更完整的页面结构变化检测和备用解析规则。
- 更多政策来源和代理配置。
- 企业微信自建应用及企业微信登录。
- 原始文件从本地文件卷迁移至正式云对象存储。

### 4.3 P2：规模化能力

- 多节点爬虫和自动容灾。
- 数据库高可用和多服务器部署。
- 业务微服务拆分。
- 申报材料协作、任务拆分和版本管理。
- 组织、部门或经营主体级数据隔离。

### 4.4 明确不进入 MVP

- 验证码破解、登录绕过或违反网站规则的采集方式。
- 任意网站 100% 自动识别承诺。
- 项目任务管理、材料版本管理和在线协同编辑。
- Kubernetes、Kafka、分布式事务等超出当前规模的基础设施。

## 5. 核心业务流程

### 5.1 政策主流程

1. 系统按日或由负责人手动触发采集任务。
2. 爬虫依次检查启用的政策来源，读取列表页和详情页。
3. 系统保存来源网址、采集时间、原始网页和附件快照。
4. 系统提取标题、文号、发布日期、申报截止日期、正文和申报条件，并进行去重。
5. 系统结合企业共享档案，分别评估北京、苏州、深圳等经营主体。
6. 系统执行硬规则、加权评分和 DeepSeek 语义分析，形成评估依据和建议结论。
7. 用户不看到“待解析”“待评估”等技术中间状态。
8. 负责人查看政策详情和评估明细，确认或修改政策结论。
9. 当结论为“建议申报”时，负责人必须同时指定主要申报主体。
10. 系统按规则发送企业微信群通知。
11. 负责人可将政策转为唯一项目，项目继承政策和主要申报主体。

### 5.2 项目主流程

项目状态为：

`待申报 → 已提交 → 成功 / 未通过 / 终止`

“申报准备”和“审核中”不作为项目状态。项目对接人只能更新自己负责的项目，申报负责人可以更新全部项目。

## 6. 政策结论与展示规则

### 6.1 用户可见结论

- 待确认
- 建议申报
- 持续关注
- 暂不建议申报
- 无法判断
- 已转项目或已归档（作为后续业务标识）

### 6.2 单一结论原则

- 政策列表和详情页只展示一个当前结论，不同时展示“系统结论”和“负责人结论”。
- AI 评估完成但未由负责人确认时，结论使用弱化或虚线视觉表现。
- 负责人确认后，使用正式、实线的状态表现。
- 多经营主体的评估结果作为明细存在，不在列表中形成多个并列状态。
- AI 重新评估不得自动覆盖负责人已经确认的结论。

## 7. 页面与交互设计决策

### 7.1 登录页

- 账号密码登录。
- 保留企业微信登录扩展入口，但 MVP 不接入。

### 7.2 政策中心

- 采用已确认的 B 方案列表布局。
- 每条政策显示名称、当前结论、发布日期和申报截止日期。
- 政策状态紧跟政策名称，保证阅读连贯性。
- 提供来源、地区、政策类型、结论、截止日期等筛选条件。
- 列表增加分页组件。

### 7.3 政策详情与评估确认

- 政策详情、评估明细和确认操作在同一页面完成。
- 信息按阅读和决策顺序连续组织，不拆成彼此割裂的大卡片。
- 确认按钮和负责人修改状态控件放在同一操作区域。
- 只显示当前结论，提供评估明细查看入口。
- 展示来源网址、发布日期、截止日期、原文和附件入口。

### 7.4 项目台账

- 不展示状态图例和说明性提示块。
- 增加分页组件。
- “3 条政策可转项目”改为文字按钮，放在申报项目总结下方。

### 7.5 企业档案

- 企业共享档案保存业务、技术和产品等公司级资料。
- 北京、苏州、深圳等经营主体分别保存注册、法人属性、资质、知识产权和研发数据。
- 首期按北京适创科技有限公司、苏州数算软云科技有限公司、深圳适创腾扬科技有限公司三个经营主体建档。北京、苏州暂按独立法人初始化；深圳主体类型因公开资料与原假设冲突，须以营业执照或国家企业信用信息公示结果终审，开发不得写死。
- “编辑档案”和“更新公开信息”放在对应经营主体区域，避免误解为全局操作。
- 研发投入比例不设置独立编辑入口，统一在经营主体档案编辑中维护。

### 7.6 政策来源

- 来源列表与添加来源操作分离。
- “添加来源”使用右侧抽屉或全局弹窗，不在页面内展开表单。
- 支持政府网站、协会网站、公众号文章链接和自定义网址。

### 7.7 评估规则

- 负责人可以编辑规则。
- 规则修改生成新版本，不覆盖历史规则。
- 已完成评估保留当时使用的规则版本。

### 7.8 移动端

- 响应式 Web 页面，不开发微信小程序。
- 移动端支持查看政策、查看评估明细和确认政策结论。
- 移动端不承担政策转项目和项目状态维护等复杂操作。

## 8. 权限设计

权限采用“角色权限 + 项目归属”两层判断。

| 功能 | 申报负责人 | 项目对接人 | 项目成员 | 产品规划团队 |
|---|---:|---:|---:|---:|
| 查看全部政策与评估明细 | 是 | 是 | 是 | 是 |
| 确认或修改政策结论 | 是 | 否 | 否 | 否 |
| 指定主要申报主体 | 是 | 否 | 否 | 否 |
| 政策转项目 | 是 | 否 | 否 | 否 |
| 编辑企业档案 | 是 | 否 | 否 | 否 |
| 编辑评估规则 | 是 | 否 | 否 | 否 |
| 配置政策来源 | 是 | 否 | 否 | 否 |
| 查看全部项目 | 是 | 是 | 是 | 是 |
| 修改全部项目 | 是 | 否 | 否 | 否 |
| 修改自己负责的项目 | 是 | 是 | 否 | 否 |
| 账号与角色维护 | 是 | 否 | 否 | 否 |

项目对接人可以更新自己负责项目的状态、提交日期、结果日期、进展说明和结果说明；不能更换主要申报主体、项目对接人或关联政策。所有关键修改必须保留操作人、时间和修改前后内容。

## 9. 核心数据对象

### 9.1 主数据

- 用户与角色。
- 企业共享档案。
- 经营主体及主体档案。
- 经营主体资质、知识产权和研发数据。
- 政策来源。
- 评估规则及规则版本。

### 9.2 过程与结果数据

- 采集任务及任务日志。
- 原始网页、附件快照及内容哈希。
- 政策及政策内容版本。
- 评估批次。
- 各经营主体的评估结果。
- AI 证据、评分和风险点。
- 负责人确认记录。
- 申报项目。
- 项目状态历史。
- 通知记录和操作审计日志。

### 9.3 核心关系

- 一份企业共享档案对应多个经营主体。
- 一个政策来源对应多次采集任务。
- 一条政策关联一个来源，并可有多个原文或内容版本。
- 一条政策可以有多次评估，每次评估包含多个经营主体结果。
- 一条政策只有一个当前结论；当结论为“建议申报”时，必须有且仅有一个当前主要申报主体，其他结论可不指定主体。
- MVP 中一条政策最多生成一个项目。
- 一个项目绑定一个主要申报主体、一个项目对接人，并可关联多个项目成员。

## 10. AI 评估设计

评估结果由三部分组成：

1. 硬规则：地区、主体类型、成立年限、资质等明确条件。
2. 加权评分：政策方向、技术匹配、企业能力、申报价值、材料准备难度等维度。
3. DeepSeek 语义分析：提取政策条件、判断企业匹配度并形成自然语言依据。

系统必须展示清晰结论，并提供评估明细入口。DeepSeek 只承担辅助分析，不是最终决策人。模型名称、接口地址和参数配置化保存，不在代码中写死；只向 DeepSeek 提供公开资料和内部非保密资料。

## 11. 政策采集设计

### 11.1 技术策略

- Scrapy 作为主要采集框架。
- scrapy-playwright 只处理必须经过浏览器渲染的页面。
- Scrapyd 负责爬虫部署、运行、停止和任务日志。
- APScheduler 每日触发采集任务。
- 重点来源采用独立适配器保证稳定性。
- 通用正文提取作为自定义网址的补充能力，不承诺适配所有网站。

### 11.2 去重与变更

- 综合使用标准化网址、标题、发布日期、文号和内容哈希判断重复。
- 同一政策重复出现时不新建重复记录。
- 已收录政策内容变化时保留新旧版本，并重新解析和评估。

### 11.3 来源健康状态

- 正常：最近一次采集成功。
- 偶发失败：本次失败但未达到通知条件。
- 连续异常：连续 3 次采集失败，需要人工检查。
- 已停用：负责人主动停止采集。

单次失败只记录在系统中；连续 3 次失败后，通过企业微信群机器人通知负责人。

## 12. 通知设计

MVP 使用企业微信群机器人，不建设企业微信自建应用。通知场景包括：

- 高匹配政策发现。
- 政策评估完成。
- 政策转为项目。
- 项目已提交。
- 项目申报成功。
- 政策来源连续 3 次采集失败。
- 每日备份失败。

通知失败需要自动重试并保留失败原因。群消息只提供摘要和系统详情入口，不承载复杂业务操作。

## 13. 技术架构

### 13.1 架构原则

采用“模块化单体 + 独立爬虫运行区”：

- 前端和业务 API 组成一个业务产品。
- 业务后端保持一个代码库，但按账号、政策、企业档案、评估、项目、通知和审计划分模块。
- 爬虫单独运行，爬虫崩溃或重启不影响政策查看、结论确认和项目管理。
- AI 评估和通知通过后台任务异步执行，页面不等待外部接口返回。

### 13.2 技术栈

| 层级 | 技术 |
|---|---|
| 前端 | Vue 3、TypeScript、Vite、Element Plus |
| 业务 API | Python、FastAPI |
| ORM 与迁移 | SQLAlchemy 2、Alembic |
| 数据库 | MySQL 8.4 |
| 爬虫 | Scrapy、scrapy-playwright、Scrapyd |
| 网页正文提取 | 来源专用规则优先，Trafilatura 兜底 |
| 定时任务 | APScheduler |
| AI | DeepSeek API 适配层 |
| 部署 | Ubuntu Linux、Docker Compose、Nginx |
| 文件保存 | Demo 使用独立文件卷；正式环境可迁移至云对象存储 |

### 13.3 数据流

`定时或人工触发 → Scrapyd 运行来源爬虫 → 原文留痕 → 字段标准化与去重 → MySQL 入库 → 多主体规则与 AI 评估 → 负责人确认 → 企业微信群通知 → 政策转项目`

## 14. 异常处理

| 异常 | 处理方式 |
|---|---|
| 网站暂时不可访问 | 自动重试；失败后记录任务结果 |
| 页面结构变化 | 停止生成政策，标记解析异常，避免错误数据进入业务流程 |
| 重复政策 | 自动跳过或关联已有政策 |
| DeepSeek 调用失败 | 自动重试并保留待重试任务，不展示技术中间状态 |
| 群机器人通知失败 | 自动重试并记录失败原因 |
| 两人同时修改项目 | 后提交者收到数据已更新提示，刷新后重新操作 |
| 不合法项目状态变化 | 阻止修改并提示允许的下一状态 |
| 备份失败 | 记录失败并通知负责人 |

## 15. 安全、备份与合规边界

### 15.1 安全要求

- 账号密码使用安全哈希保存。
- 连续错误登录受到限制。
- MySQL 不直接暴露到互联网。
- 公网只开放 HTTPS；SSH 仅允许必要的管理来源访问。
- DeepSeek 密钥、群机器人地址和数据库密码通过环境配置管理，不写入代码。
- 关键业务操作具有权限检查和审计记录。

### 15.2 备份

- 数据库、原始网页和附件每天异地备份一次。
- 保留最近 7 天备份。
- 上线前必须完成一次数据库和文件恢复演练。
- 该方案最多可能损失一天内的新数据和操作记录。

### 15.3 Demo 数据边界

- Demo 使用个人云账号，只保存公开信息、虚构测试数据和公司内部非保密资料。
- 不在个人账号中存储公司保密资料或正式生产数据库。
- Demo 使用独立 API 密钥，迁移正式环境时必须更换。

### 16.2 正式环境迁移

正式上线前迁移至公司企业账号下的中国内地标准 CVM/ECS，使用公司域名、HTTPS 和单位主体备案。迁移步骤为：创建公司服务器、安装 Docker、部署应用、恢复 MySQL、迁移原始文件、更换域名与密钥、完成验收后停止个人服务器。

## 17. 测试与上线验收

### 17.1 业务验收

1. 5 个重点来源能够完成采集、去重和原文追溯。
2. 一条政策能够完成多主体评估和负责人确认。
3. 确认建议申报时必须指定主要申报主体。
4. 一条政策只能生成一个项目。
5. 项目对接人只能更新自己负责的项目。
6. 企业微信群机器人能够发送业务通知和连续异常提醒。
7. 政策列表只显示一个当前结论。
8. 用户看不到待解析、待评估等技术中间状态。

### 17.2 技术验收

1. 密码安全保存，登录错误受到限制。
2. MySQL 不直接暴露到互联网。
3. 外部密钥不写入代码或提交到版本库。
4. 爬虫、AI 和通知失败均可重试并留有日志。
5. 关键操作具有权限检查和修改历史。
6. 服务重启后不会重复处理同一政策。
7. 完成一次备份恢复演练。
8. 15 名以内用户进行核心页面操作时保持正常响应。

## 18. 实施顺序建议

首期采用“真实纵向闭环优先”的路线，不先铺开大量页面或来源：

1. 建立账号、企业档案、经营主体和政策来源基础能力。
2. 打通 1 个真实来源的采集、留痕、解析和政策入库。
3. 打通多主体评估、DeepSeek 分析和负责人确认。
4. 打通企业微信群通知和政策转项目。
5. 完成项目台账、项目权限和状态历史。
6. 扩展至 5 个重点来源并完成异常、备份和验收。

## 19. 已确认业务假设

- 公司约 200 人，系统首期使用人数为 5—15 人。
- 科技项目或政府项目申报是公司业务方向之一，不将系统设计为单一申报工具平台。
- 所有内部用户可查看全部政策和项目。
- 申报负责人首期可由同一个人承担政策确认、业务配置和项目统筹。
- 只使用公开企业信息和公司内部非保密资料进行评估。
- 首期每日采集一次，优先保障 5 个重点来源。
- 自定义网址提供通用解析能力，但重点来源需要独立适配。
- 项目管理只做轻量台账，不做材料协同和任务管理。
- Demo 部署可接受服务器故障时短暂中断，重点保证数据可恢复。
