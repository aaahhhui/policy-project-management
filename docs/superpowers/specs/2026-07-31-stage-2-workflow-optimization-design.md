# Stage 2 流程优化设计

## 1. 目标

在不改变 Stage 2 核心评估模型的前提下，补齐人工决策、评估取消、状态自动刷新和可理解的历史展示，使负责人能够完成可追溯、无歧义的政策决策闭环。

本次优化包括：

1. 评估状态自动刷新。
2. 主动取消评估，并区分“已取消”和“评估失败”。
3. 历史批次使用“第 N 次评估”作为主标题。
4. 规则发布失败显示具体中文校验原因。
5. 负责人在确认评估时选择最终政策结论。
6. “建议申报”结论与主申报企业在同一表单、同一事务中确认。
7. 已确认政策允许负责人追加式调整结论。
8. 展示当前结论的来源和确认时间。

不在本次范围内：政策转项目、项目台账、企业微信通知、账号管理和新增政策来源。

## 2. 核心业务规则

### 2.1 系统建议、人工结论与主申报企业

- 评估批次保存模型生成的系统建议和三家企业结果，模型原始结果保持不可变。
- 政策当前结论是负责人确认后的有效业务结论。
- 主申报企业是独立决策；确认或切换主申报企业不得自动改变政策结论。
- 负责人确认评估时可以接受或修改系统建议。
- 当最终结论为“建议申报”时，必须在同一确认表单中选择一家主申报企业。
- “持续关注”“暂不建议申报”“无法判断”不强制选择主申报企业。
- 已确认后切换主申报企业仍沿用现有规则：选择其他候选企业时必须填写切换原因。
- 已确认后调整政策结论必须填写原因。
- 后续重新评估只产生新的系统建议，不得覆盖当前人工结论。

### 2.2 评估取消

- 申报负责人可以取消状态为“等待中”或“评估中”的批次。
- 取消原因非必填；填写后必须保存并进入审计记录。
- 已进入待确认、已确认、已取消或失败状态的批次不能取消。
- 重复提交相同批次的取消请求保持幂等。
- 评估工作进程在提交模型结果前必须再次锁定并检查批次状态。若批次已取消，应丢弃迟到结果，不得覆盖取消状态或政策当前状态。

## 3. 数据模型

### 3.1 政策结论决策

新增 `policy_conclusion_decisions` 表，采用追加式记录：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `policy_id` | 政策 ID |
| `evaluation_batch_id` | 关联评估批次；人工后续调整沿用当前有效批次 |
| `previous_conclusion` | 调整前结论 |
| `conclusion` | 调整后结论 |
| `source` | `evaluation_confirmation` 或 `manual_override` |
| `reason` | 评估确认时可为空；人工后续调整时必填 |
| `decided_by` | 操作人 |
| `decided_at` | 操作时间 |

现有 `policies` 表增加：

- `current_conclusion_source`：`system_suggestion`、`evaluation_confirmation` 或 `manual_override`。
- `conclusion_confirmed_at`：当前人工结论的确认时间。

迁移时通过 `evaluation_confirmations → evaluation_batches → policy_versions → policies` 的关联，为每个已有确认记录补写一条 `evaluation_confirmation` 来源的决策；`previous_conclusion` 使用该批次原始模型结论，操作人和时间使用原确认记录。迁移完成后，政策详情统一读取结论决策，不保留双路径回退。

### 3.2 评估取消

评估状态枚举增加 `cancelled`。`evaluation_batches` 增加：

- `cancelled_by`：可空用户外键。
- `cancelled_at`：可空时间。
- `cancel_reason`：可空文本，最长 2000 字符。

取消操作同时写入 `evaluation_cancelled` 审计事件。

## 4. 后端接口与事务

### 4.1 确认评估

扩展 `POST /api/evaluations/{batch_id}/confirmation`：

```json
{
  "conclusion": "recommend_apply",
  "summary": "人工确认后的摘要",
  "key_conditions": [],
  "entities": [],
  "change_reason": "调整模型建议的原因",
  "primary_entity_seed_code": "ENTITY-SHENZHEN"
}
```

- `primary_entity_seed_code` 可空。
- 结论为 `recommend_apply` 时该字段必填，且必须属于本批次三家候选企业。
- 修改模型建议时继续要求 `change_reason`。
- 一次事务内完成：评估确认、政策结论决策、政策当前结论更新，以及必要时的主申报企业确定。
- 任一校验失败时全部回滚。
- 等价重复请求保持幂等。

### 4.2 取消评估

新增 `POST /api/evaluations/{batch_id}/cancellation`：

```json
{
  "reason": null
}
```

- 仅 `applicant_owner` 可调用。
- 等待中或评估中可取消。
- 已取消批次重复调用返回当前取消结果。
- 其他终态返回 `409 evaluation_cancellation_conflict`。

### 4.3 调整政策结论

新增 `POST /api/policies/{policy_id}/conclusion-decisions`：

```json
{
  "conclusion": "watch",
  "reason": "当前申报材料尚不完整"
}
```

- 仅 `applicant_owner` 可调用。
- 原因去除首尾空白后必须非空，最长 2000 字符。
- 政策必须已有已确认评估。
- 调整为 `recommend_apply` 时必须已有当前主申报企业。
- 新增决策记录并更新政策当前结论、来源和确认时间。
- 相同结论仍视为一次人工决策，但必须填写原因并保留历史。

新增 `GET /api/policies/{policy_id}/conclusion-decisions`，已登录用户可查看按时间倒序排列的结论历史。

## 5. 前端交互

### 5.1 自动刷新

- 详情页当前批次为 `pending` 或 `running` 时，每 3 秒调用评估历史接口。
- 页面卸载或进入终态时立即停止定时器。
- 同一时刻最多存在一个刷新请求；前一请求未完成时不发起下一请求。
- 刷新失败显示非阻断提示，下一周期继续重试。
- 当前结论已由人工确认时，轮询得到的新系统建议不得覆盖标题区域的人工结论。

### 5.2 取消评估

- 等待中或评估中显示“取消评估”。
- 点击后打开确认弹窗，取消原因为可选文本框。
- 提交期间按钮禁用。
- 成功后立即显示“已取消”和可选取消原因。
- 只读账号不显示取消入口。

### 5.3 评估确认与人工结论

- 确认表单增加“政策处理结论”单选或选择控件。
- 选择“建议申报”后显示并要求选择主申报企业。
- 修改模型结论或企业评分时，修改原因必填。
- 原样接受模型结论且不修改评分时，原因可空。
- 确认成功后显示当前有效结论、来源“负责人确认”和确认时间。
- 已确认区域提供“调整政策结论”；调整弹窗原因始终必填。
- 只读账号只显示当前结论和结论历史。

### 5.4 历史与错误文案

- 当前批次和历史批次按政策内创建时间升序计算序号。
- 主标题显示“第 N 次评估”，次要信息显示“批次 #ID”。
- `cancelled` 显示“已取消”，`failed` 显示“评估失败”。
- 失败摘要不显示敏感内部异常；取消原因存在时可显示。
- 规则发布失败根据服务端错误码显示具体中文提示，例如权重不等于 100、缺少启用条件、版本不可发布。

## 6. 并发与错误处理

- 确认、取消、模型结果提交和人工结论调整均锁定目标政策或批次行。
- 状态转换由后端决定，前端按钮禁用仅作为体验优化。
- 取消与模型回写竞争时，先提交的终态获胜；模型工作进程检测到 claim 丢失或批次已取消后丢弃结果。
- 确认与取消竞争时，仅一个操作成功，另一个收到明确 `409`。
- API 返回稳定错误码；前端将已知错误码映射为中文业务提示，未知错误使用通用提示。
- 任何错误响应不得包含 API Key、Authorization 请求头或模型原始敏感元数据。

## 7. 权限与审计

- `applicant_owner`：确认评估、选择主企业、调整结论、取消评估。
- 其他已登录角色：查看评估、取消信息、结论来源和结论历史。
- 审计事件至少包括：
  - `evaluation_cancelled`
  - `evaluation_confirmed`
  - `policy_conclusion_changed`
  - `primary_entity_selected`
  - `primary_entity_changed`
- 审计变化内容包含业务对象 ID、前后结论、企业编码和可选原因，不包含模型密钥或认证信息。

## 8. 测试与验收

### 8.1 后端

- 迁移升级、降级和既有数据兼容。
- 取消等待中/评估中批次、重复取消、终态冲突、权限和审计。
- 取消后迟到模型结果被丢弃。
- 确认“建议申报”缺少企业时拒绝。
- 确认结论与选择企业的事务原子性。
- 人工调整结论的原因、权限、主企业前置条件和历史。
- 重评不覆盖人工结论。

### 8.2 前端

- 轮询启动、单飞、停止、失败重试和组件卸载清理。
- 取消弹窗可空原因、提交状态和终态显示。
- 确认结论与主企业联动校验。
- 人工结论调整与历史显示。
- 规则发布错误码中文映射。
- “第 N 次评估”、批次号、“已取消”和“评估失败”文案。
- 负责人和只读账号权限。

### 8.3 运行验收

- 后端测试、前端测试、类型检查和生产构建通过。
- MySQL 迁移在 Stage 2 Compose 环境验证。
- 8081 完成负责人和只读账号人工冒烟。
- 验证取消与模型回写竞争、确认“建议申报”并同时选择企业、后续人工调整结论、审计历史。
- 扫描日志和版本库，确认不包含 DeepSeek API Key 或 Authorization 请求头。
